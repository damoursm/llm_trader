## Running the pipeline

```bash
python main.py                # Run once, console output only
python main.py --email        # Run once and send email report
python main.py --schedule     # Start the poll-loop runner (RTH every 30 min 9:30–16:00 ET + extended trading ticks 4:00–19:50 + overnight ticks 20:30–03:30 hourly on the overnight venue's own Sun–Thu-night calendar; NYSE market days for rth/extended; emails at the `scheduler_email_times` slots — default 04:00/09:30/16:00/19:50 ET; `scheduler_email_every_tick` overrides → every slot; empty `scheduler_email_times` → only the 16:00 close. Once per market day at/after `eod_maintenance_time` 16:20 ET the loop runs EOD maintenance — forward-return OHLCV cache warm (fuel for the IC panels / policy evals / calibrations / the post-exit forward-return monitor — recently-EXITED trade tickers stay warmed too, `data/cache_warm.py`) + `simulated_trades` retention (collapse old intraday bloat, age-prune, `db/retention.py`) — off the time-critical path, `enable_eod_maintenance`)
python main.py --supervise    # PRODUCTION (this is what scripts/run_scheduler.bat launches): run --schedule under an external auto-restart supervisor (src/scheduler/supervisor.py) that relaunches the scheduler if the process dies (it died silently — no traceback — under the kaleido email crash; and it recovers the broker-sync watchdog's `os._exit(1)` force-kill, see the broker section). NOTE a HANG (frozen process that never exits — e.g. the 2026-07-06 stuck-broker-request freeze before the RequestTimeout fix) is NOT caught by --supervise NOR by Task-Scheduler restart-on-failure: both need the process to actually exit. The broker watchdog exists to turn that hang class into an exit. To STOP a supervised scheduler, kill the `--supervise` parent FIRST (so it can't respawn), then the `--schedule` child.
python main.py --dashboard    # Launch the read-only monitoring dashboard (Plotly Dash via waitress; in-process auto-restart)
python main.py --backfill     # Pre-warm the OHLCV caches for the WHOLE universe via Massive/Polygon (deep daily history), then exit (add --backfill-30m to also warm the 30-min cache). Additive — merges into cache/ohlcv/, never deletes. Standalone: `python -m src.data.backfill [--days 730] [--with-30m] [--skip-daily] [--signal-days 90]` (`--skip-daily` = 30-min-only top-up when daily is already warm). WEEKLY needs no pass — it is resampled from the daily cache on demand, so a deep daily backfill gives deep weekly automatically. 30-min depth is Polygon-capped (~120 days via `intraday_30m_lookback_days`).
```

Logs go to `logs/llm_trader_YYYY-MM-DD.log` (7-day rotation). The HTML report (when `ENABLE_CHARTS=true`) is saved to `logs/report_YYYY-MM-DD_HHMM.html`.

To force a fresh run ignoring caches, delete `cache/news_*.json` and/or `cache/snapshots_*.json`. The OHLCV cache (`cache/ohlcv/`) and the DuckDB database (`data/llm_trader.db` — trades, recommendations, run history) should never be deleted casually.

**Trailing-NaN bar guard (2026-07-25, `cache.trim_trailing_nan_bars`, applied at PARSE time inside `load_ohlcv`; `market_data._trim_trailing_nan_bars` is a thin alias called first in `_drop_forming_bar` for frames that came straight from a provider fetch).** Placed at the cache-read entry point rather than only in `market_data` because several scorers read `load_ohlcv` DIRECTLY and would otherwise stay exposed — `agreement`'s tape confirmation (which feeds the confidence multiplier on EVERY ticker: measured going silently from `BULLISH_TAPE 0.704` to `NO_DATA` on one trailing NaN bar — fail-SAFE, but ~17 tickers a run losing the signal for nothing), plus `classic_anomalies`, `anchored_vwap`, `cointegration` and `extended_session` (the last three measured UNaffected, but the exposure was structural). The trim runs once per PARSE and the frame is then memoised, so the hot path is unchanged. yfinance appends a row with a NaN Close for the still-forming bar, and **~1% of cached daily frames carry one** (AMN/APTV/AZO/AZTR at the time of writing). It holds no information, but an indicator handed one does not fail — it returns a DIFFERENT number, silently: measured on an identical 260-bar rising series, one appended NaN bar moved **5 of 6 OHLCV scorers** — `tech` (weight 0.30, rank 2) −0.065 → **+0.400**, a 0.47 swing that FLIPS its sign; `iv_rank` 0.127 → **0.000**, zeroed outright; `trend_strength` 0.729 → 0.600; `momentum` 0.994 → 1.000; `money_flow` −0.391 → −0.392. Trimming restores every score EXACTLY. Only the TAIL is trimmed and only on a missing Close: **interior NaNs are left alone** (a real gap in a real series — measured drift ≤0.04, and dropping them would silently change bar spacing). Same NaN-tail shape that once made `is_liquid` gate out liquid large caps. NOTE the guard lives at the market_data boundary, not inside each scorer — handed a raw all-NaN frame, `tech`/`money_flow`/`trend_strength` still fabricate a view (+0.40/−0.58/+0.20), so scoring must never bypass `get_history`. Tests: `tests/test_scorer_contract.py`.

**Coverage & the actionable-gate extraction (2026-07-25).** `pip install coverage pytest-cov`, then `python -m pytest -q --cov=src --cov=config --cov-report=json:cov.json -p no:randomly` (artifacts are gitignored). Overall is **54.6%**, but the raw percentage is nearly useless here — most of the uncovered mass is `src/data/*` network fetchers (9–20% each), which are I/O wrappers whose liveness the runtime `data_quality` monitor already watches. The exception was decisive — **the actionable filter (Gates 1, 1b, 2, 3, 4, 5) had ZERO coverage: 0 of 31 statements.** The gate HELPERS (`_is_tradeable` / `_is_overextended` / `_passes_agreement_gate`) were well tested, but nothing exercised the loop that SEQUENCES them, so a wrong gate order, a missing `continue`, or a mis-attributed counter would have been invisible in the code that decides what actually trades. It was therefore extracted from `run_pipeline` into **`_apply_actionable_gates`** — behaviour-preserving (same gates, same order, same counters, same `gate_outcomes` stamps; `gate_diag`/`gate_outcomes` still mutated in place) purely to make it reachable from a test. Now **36 covered / 0 missing** (`tests/test_actionable_gates.py`, 14 tests), pinning each gate in isolation AND the two subtler properties: a drop is attributed to the FIRST gate that rejects it (`compute_stage_eval`'s funnel reads those stamps, so mis-attribution corrupts the which-gate-filters-losers analysis even when the trade decision is right), and an expensive gate is never consulted after an earlier one rejected the candidate (`_is_tradeable` can trigger a network fetch). NOTE the same sweep found `tests/test_agreement_gate.py` asserting on the SOURCE TEXT of `run_pipeline` — it broke on the extraction despite identical behaviour, and would have passed on code containing the right string that never executed (which is exactly what it was guarding, at 0% coverage). Rewritten to drive the real function; it was the only `inspect.getsource` assertion in the suite.

**Scorer contract tests (2026-07-25, `tests/test_scorer_contract.py`).** `pattern_recognition` (349 LOC, weight 0.18, rank 5 of 21) had ZERO tests — it appeared in the suite only as a flag being switched off. Rather than bespoke tests for one module, the contract is asserted across ALL OHLCV scorers through `multi_timeframe._score_one`, the single uniform entry point, so a new scorer is covered the moment it joins `TECHNICAL_METHODS`: (1) score within `[-1,+1]`; (2) **responds to a MIRRORED tape** — a scorer returning the same number for a rising series and its mirror cannot express direction at all, exactly the `money_flow` bug of 2026-07-24; (3) degenerate frames (empty / 1-row / 5-row / all-NaN) yield NO VIEW rather than a fabricated direction — `_score_one` swallows exceptions into `None`, which silently DROPS the method from the frame, so a crash there is invisible in production. Two documented exemptions: `sector_momentum` ignores the passed frame by design (it re-fetches both legs at the interval), and `pattern` needs a learned library (`cache/patterns/`, 43% populated, median 2 patterns) so it correctly returns 0.0 for an unlearned ticker.

**Intraday operation (no unclosed-bar look-ahead).** The scheduled runner ticks **every 30 min, 9:30–16:00 ET** on NYSE market days (weekends AND holidays skipped via `market_calendar.is_market_day`). The pipeline marks and fills on **live** prices (`_fetch_price` → `fast_info.last_price`); the daily OHLCV feeding the indicators is **completed-bars-only** — `market_data._drop_forming_bar` removes the still-forming current-session bar until the 16:00 close, so no indicator or NAV walk ever reads an unclosed daily bar. Open-position NAV is **marked to the live price each tick** (`daily_nav._build_marks` uses `current_price` as the open-trade end anchor). A **Hybrid** intraday-timing overlay (`src/signals/intraday_timing.py`) affects entry/exit *timing* only: it defers an entry whose 30-min momentum strongly opposes it (`enable_intraday_timing`, default on) and can close on a hard intraday reversal (`enable_intraday_exit`, opt-in → `exit_reason = "intraday_reversal"`); during extended sessions it fetches `prepost=True` bars so the gate reads the live extended tape, not yesterday's last RTH bar. It never changes the daily-signal direction.

**Extended hours (Phase 1 — TRADING, on by default).** `extended_hours_mode` = `off | observe | trade` (default **`trade`**). The runner ticks through the FULL extended day per `extended_windows` (default `04:00-07:00@60,07:00-09:30,16:00-17:30,18:00-19:00@60,19:50-19:50` ET — liquid shoulders every 30 min, thin dead zones hourly via the `@MM` per-window cadence suffix; a window with equal endpoints is a SINGLE slot, and the **last after-hours tick is 19:50, not 20:00**: the pipeline takes minutes from tick to order submission (~4–7 min after the 2026-07-08 latency work — the opener-pinned hold-review now runs CONCURRENTLY with Steps 4–5 via `enable_hold_review_overlap`/`pipeline._HoldReviewBranch` instead of adding ~2.5 min serially after them), so the final slot leaves a ~10-min pre-close buffer; a 20:00/19:55 slot's orders reached IBKR after the session close and could never fill same-day). In **trade** mode extended slots are FULL trading ticks (`_tick_plan` in `runner.py`): ledger entries/exits/marks and broker paper orders happen off-hours too; in **observe** mode (Phase 0) they run `run_pipeline(observe_only=True)` — full analysis + DuckDB persistence but zero ledger/broker mutation. **Email gating (`_tick_plan`):** the report emails at the slots whose ET time is in `scheduler_email_times` (default **`04:00,09:30,16:00,19:50`** — pre-market open / RTH open / RTH close / last after-hours tick; each must be a real tick slot, else it never fires — the scheduler logs a startup warning for any that aren't). Precedence: `scheduler_email_every_tick` on ⇒ EVERY slot emails (~28/day) — **this is the LIVE production setting (`.env` `SCHEDULER_EMAIL_EVERY_TICK=true`, deliberate as of 2026-07-25), so the four-slot default below is documentation-only and is NOT what runs**; else the `scheduler_email_times` set; else (when that's empty) only the 16:00 closing RTH slot. Either way the scheduler passes `email_if_configured=False` so its per-slot decision is authoritative — manual `python main.py` runs keep the email-if-configured convenience. **Problem override (`email_on_problem`, default ON):** independent of the slot / every-tick gating, any tick that detects a PROBLEM — a broker/execution issue (disconnect, rejects, drift), an LLM-layer outage (credits/keys), or a price-provenance flag (the same three health verdicts behind the 🔔 subject tags + email banners) — FORCES the report email OUT OF SCHEDULE (`pipeline._email_decision`, gated on email being configured), so an issue surfacing between the scheduled slots reaches you at the next ~30-min tick instead of hours later. Observe-only ticks stay silent by design. A persistent problem re-alerts each tick until it clears.

Session classification (`market_calendar.current_session` → `rth | extended | overnight`) is fixed once per run. **`enable_extended_signal_profile` (default OFF) governs whether the session changes the SCORE.** With it **OFF (default)** scores are **comparable across the trading day** (the requirement behind the fix #2 confidence trajectory): ONE fixed weight profile is used every session (no overlay), `ext_gap` is in the active method set in ALL sessions (identical method set + weight normalisation; it still reads 0.0 in RTH by design), and the synthesis prompt carries NO session-context block. With it **ON** it restores the original **extended signal profile**: (1) aggregator weight overlay — options-derived methods (`put_call`, `max_pain`, `oi_skew`, `iv_expr`) ×`extended_stale_options_weight_mult` (0.5 — chains frozen at the RTH close) and `news`/`sent_velocity`/`ext_gap` ×`extended_news_weight_mult` (1.25); (2) `ext_gap` off-hours-only; (3) a session-context block in the Claude prompt (thin books, frozen options data, news/gap = live information). The **ext_gap scorer** itself (`src/signals/extended_session.py`) — live extended print vs last completed close in ATR units, tanh-scaled with a deadband, always 0.0 during RTH, fail-closed on a stale OHLCV cache — is unchanged. **Independent of the flag** (GATES/sizing, not scores, so they don't affect score comparability): `extended_confidence_bump` (+6 pp on the actionable threshold — set to 0.0 for session-invariant actionability) and `extended_size_multiplier` (×0.5 off-hours sizing). Snapshot prices are genuinely extended off-hours (Polygon `lastTrade` includes extended prints; the yfinance fallback pulls 1-min `prepost` bars).

**Overnight session (2026-07-02 — TRADING, on by default).** `overnight_hours_mode` = `off | observe | trade` (default **`trade`**) makes the OVERNIGHT session (20:00→04:00 ET) a first-class trading period on IBKR's overnight venue calendar — **Sun–Thu nights, 20:00–03:50 ET** (`market_calendar.is_overnight_session_open`; Friday/Saturday/holiday-eve nights have NO session and are never ticked or booked — slot validity is per-slot in `runner._slot_is_valid`, so Sunday-evening slots tick even though Sunday isn't a market day). Slots come from `overnight_windows` (default `20:30-23:30@60,01:00-03:00@60,03:30-03:30` — hourly; the 03:30 single slot is the last tick whose orders can work the book before the venue's 03:50 close, mirroring the 19:50 rule). Overnight trades carry the harshest terms in the stack: modeled spread ×10 (`spread_overnight_multiplier`), entries sized ×`overnight_size_multiplier` (**0.25**, vs extended's 0.5), and the actionable threshold bumped by `overnight_confidence_bump` (**+10 pp**, replacing — not stacking with — the extended +6 pp). **Broker overnight:** live-overnight-session orders route to IBKR's overnight venue (`broker_overnight_routing`, default on → `OrderRequest.overnight` → contract exchange `"OVERNIGHT"` instead of SMART, LMT-only, no `outsideRth` flag, cap `broker_limit_cap_bps_overnight` = 150 bp; ~10k eligible US stocks/ETFs — an ineligible symbol rejects fail-soft as SUBMIT_FAILED and the tick-scoped lifecycle retries/kills). **Venue routing VALIDATED 2026-07-14** — but it REQUIRES the gateway's API precaution bypasses: the "Redirect Order warning" precaution silently DISCARDED every direct-routed OVERNIGHT order for 2 weeks (Error 10329 → instant `Cancelled`, 118 orders/38 tickers, zero fills) while the app recorded bare "Cancelled" and mislabeled them rejects. Root fix = `C:\IBC\config.ini` `BypassOrderPrecautions=yes` + `BypassRedirectOrderWarning=yes` (+ the other stock bypasses), which IBC re-applies at EVERY gateway launch, so the fix survives restarts; verified by a 1-share SPY probe resting Submitted on the venue. Hardening: `ibkr._trade_log_reason` now records IBKR's actual cancel/reject reason from `trade.log` into `broker_orders.error` (no more bare "Cancelled"), and a genuinely-refused overnight order (ineligible symbol, closed book) counts as `overnight_deferred` — INFO log, resubmitted at the 04:00 pre-market open, NOT a reject, so it can never fire the broker-health CRITICAL/email (`reconcile._tally_submit_failure`; real rejects and gateway timeouts still alert).

**Extended trade lifecycle:** `_execution_iso()` returns *now* during RTH, during extended sessions in trade mode, AND during the live overnight session in overnight trade mode (those fills are real); closed-venue nights (Fri/Sat/holiday-eve), weekends, and observe-mode timestamps still snap to the next regular open. Every entry stamps `entry_session` (+ the session's sizing haircut — ×0.5 extended / ×0.25 overnight by default — on top of the confidence tier and correlation haircut); every close stamps `exit_session`. Costs are session-aware end to end: spread multipliers ×4 extended / ×10 overnight (`spread._session_spread_multiplier`), per-leg `entry_session`/`exit_session` in `_pct_return`, the daily-NAV anchors, `_normalize_closed_returns`, `_flip_trade`, and the live M2M (`update_open_trades` charges the *current* session's exit cost; the NAV open-anchor uses `_session_of_mark`). **Broker off-RTH:** `reconcile.sync()` forces a marketable **LMT** outside regular hours (IBKR rejects MKT there) — extended sessions get `outsideRth=True` at the extended cap; the live overnight session routes to the overnight venue (above); RTH keeps the configured `broker_order_type`. A non-routable overnight submission (routing off / venue closed) rests until the 04:00 pre-market open, where the tick-scoped lifecycle kills-and-re-decides it.

**Session-split evaluation:** every perf surface accepts `session=` — the dashboard's Entry Performance and Returns tabs each carry an RTH/Extended/Overnight toggle, trade tables show a `Session` column, the email/dashboard performance breakdown adds per-session rows (group `session`, shown once any non-RTH trade exists), and `_compute_llm_perf` pseudo-trades charge the extended entry leg.

## Architecture

### Pipeline flow (`src/pipeline.py`)

`run_pipeline()` is the single entry point. Steps execute in sequence:

```
0.  Universe construction   — Static watchlist (ALWAYS included and never gated: `trending.get_trending_tickers` returns `base_tickers + base_sectors + extras`, watchlist FIRST, and Section F's `_protected` set exempts it from the discovery liquidity gate — so a pinned name is scored + persisted to the `signals` panel every tick regardless of price/volume or any actionable gate; see the Per-ticker simulated performance table) + dynamic discovery (trending, screener, macro→holdings, catalyst/analyst/earnings expansion, related-company peers (Massive `src/data/related_companies.py`, seeded from watchlist + held names)). The discovery gate then (a) drops junk tickers (`is_valid_ticker` — "N/A" etc.), (b) drops exotic security TYPES (`is_exotic_security` — preferred series, warrants, units, rights, OTC foreign ordinaries; ADRs/class-shares kept), and (c) filters microcaps by price + 20-day $-volume against the **OBSERVATION floor** (`discovery_min_price` **$1** / `discovery_min_dollar_volume` **$1M** — kept LOW so penny / thin-volume names ENTER the universe and keep accruing performance data for the predictability + price/volume panels; dollar-volume is the main universe-SIZE lever). **Two-tier liquidity (2026-07-08):** a name that clears this observation floor but sits below the HIGHER **TRADE floor** (`trade_min_price` **$5** / `trade_min_dollar_volume` **$5M**, `enable_trade_liquidity_gate`) is **OBSERVE-ONLY** — fully scored + persisted to the `signals` panel but gated out of actionable trades by **Gate 4** of the actionable filter (`pipeline._is_tradeable`, fail-closed via `is_liquid`, counted as `gate_diag.dropped_untradeable`), so it never opens a sim trade or broker order. So penny-stock performance keeps being monitored while only $5+/$5M+ names actually trade. The pinned watchlist bypasses the **DISCOVERY** gate only (`pipeline`'s Section-F `_protected` set — watchlist + sector ETFs + commodities + factor ETFs + open-trade tickers are never dropped from the universe), **NOT Gate 4**: `_is_tradeable` applies `is_liquid` unconditionally, so a pinned name below the $5 / $5M TRADE floor is still scored and persisted but stays OBSERVE-ONLY and never opens a trade. Pinning a thin name gets it analysed, not traded.
1.  News & sentiment feeds  — RSS (CNBC/Seeking Alpha/Yahoo) + press-release wires (GlobeNewswire/PR Newswire) + FDA/MedWatch regulatory feeds + per-ticker Google News (with a Business Wire site-query) — all fetched FRESH every tick (never cached) for fast catalyst reaction — plus NewsAPI, per-ticker yfinance news, Polygon (Benzinga) + Finnhub provider news, Alpha Vantage news-sentiment (off by default), StockTwits (off by default), 8-K filings, Google Trends, Reddit, Quiver alt-data, analyst ratings, EPS surprises, short interest, Massive ticker events (recent renames/delistings on held + watchlist names, pre-scored: delisting=negative, rename=neutral — protective, so a symbol change can't silently strand a position; `src/data/ticker_events.py`, `enable_ticker_events`). All normalised to NewsArticle; the merged pool is URL-deduped.
2.  Market snapshots        — Polygon/Massive batch primary (REAL-TIME full-market on the Stocks Advanced plan → `price_source="live"`; the snapshot endpoint 403s only on the free tier); yfinance per-ticker fallback; then a DETERMINISTIC grouped-daily close fallback (one Polygon `/v2/aggs/grouped` call, free-tier-friendly — fills any uncovered ticker with the last completed close, marked `price_source="prev_close"`). Indices/futures/OTC route through yfinance. (Execution prices come separately from `tracker._fetch_price`, IBKR-first.)
3.  Smart-money + macro     — Insider/congressional trades, options flow, SEC filings (13D/G, Form 144, 13F, Form 4), plus market-context fetchers (FRED, COT, VIX, MOVE, DIX, breadth, credit, bond/global macro, sector rotation, business cycle, etc.).
3X. Regime & timing layers  — Macro Regime Filter, Market Mode, Catalyst Timing — gate BUYs, adjust thresholds, and tweak aggregator weights.
3#. Per-ticker scorers      — News sentiment, sentiment velocity, technical, trend strength, momentum, money flow, pattern recognition, IV rank/expression, PEAD, cointegration, cross-sectional rank, extended-session gap (off-hours runs only), broker advisor (IBKR short-borrow, when `enable_broker_advisor` + a live broker), and the trend-predictability methods (signed Kaufman efficiency ratio + ADX·DMI, four methods by trend context — `*_long`=uptrend / `*_short`=downtrend — each scaled by a LEARNED continuation-vs-reversal orientation; `src/signals/trend_predictability.py`, `enable_trend_predictability_methods`), plus the **classic anomalies** (2026-07-08, PANEL-FIRST at weight 0 — `src/signals/classic_anomalies.py`): `hi52` 52-week-high proximity (George-Hwang continuation), `mom_12_1` 12-1 skip-month momentum (Jegadeesh-Titman), `st_reversal` 1-week reversal (sign-flipped, `st_reversal_min_dollar_volume` $50M liquidity floor, z deadband), plus the **Tier-2 panel-first methods** (same date/contract): `squeeze` TTM Squeeze (BB(20,2σ) coiling inside Keltner(20,1.5×ATR); the release fires in Carter-momentum direction, coil = small anticipatory score ×0.35; `src/signals/ttm_squeeze.py`), `iv_term` IV term-structure slope (front vs back ATM IV captured FOR FREE during the GEX chain fetch — `GEXSignal.atm_iv_front/back` + DTEs, old caches → NO_DATA fail-soft; backwardation = bearish tilt; `src/signals/iv_term_structure.py`), `avwap` Anchored VWAP from the 52-week high/low anchor days (POSITIONING read: above the anchor = support = bullish — deliberately the OPPOSITE sign of the mean-reversion rolling `vwap` method; `src/signals/anchored_vwap.py`), and the **Tier-3 pair** (same date/contract): `resid_mom` Residual Momentum (Blitz-Huij-Martens 2011 — 12-1 momentum on the residual of a TRUE-beta 252d regression vs SPY, so a high-beta name gets no free momentum credit, unlike sector/market momentum's implicit beta=1; `src/signals/residual_momentum.py`) and `vol_profile` Volume Profile (60d volume-at-price histogram → POC + 70% value area; acceptance outside value = trend score, inside value = small ×0.35 POC-gravity; `src/signals/volume_profile.py`). All EIGHT panel-first methods are scored on every ticker + IC-tracked + trade-attributed but deliberately EXCLUDED from combined_score/coherence/sources_agreeing AND the exit consensus (`exit_conviction._CONSENSUS_SKIP`) until the Signal-IC panel earns them a weight (`enable_high_52w`/`enable_momentum_12_1`/`enable_st_reversal`/`enable_ttm_squeeze`/`enable_iv_term_structure`/`enable_anchored_vwap`/`enable_residual_momentum`/`enable_volume_profile`). Each returns a score in [-1, +1].
3B. Broker advisor group    — `src/signals/broker_advisor.py` (`enable_broker_advisor`, default OFF — needs `broker_mode != off`). The first method in a broker-aware group and the ONLY method aware of IBKR-unique data. v1 scores SHORT-BORROW state: hard/expensive-to-short (low/zero `shortable_shares` via IBKR tick 236, or a high borrow `fee_pct`) is a squeeze tell → BULLISH (`+`, capped at `broker_advisor_max_score`), which fades a SELL and mildly reinforces a squeeze-long; easy borrow / no data → 0 (a one-sided signal — bullish or no-view, never bearish). `BorrowInfo` + `Broker.get_short_borrow` (`src/broker/base.py`, IBKR impl in `ibkr.py` — best-effort, NEEDS a live-gateway smoke-test); the pipeline fetches a capped set (`broker_advisor_max_tickers`) via `fetch_borrow_context` before `build_signals` (fail-soft → method inactive). Decision-only — never places an order. Weighted at 0.10 (auto-tuned by the shadow-IC framework once a track record accrues). Account-aware sizing, the IBKR scanner for new-ticker discovery, and an LLM advisor are the planned next methods in this group.
3M. Massive technicals (cmp)— Massive/Polygon server-side RSI+MACD composite (`src/signals/massive_tech.py`, 2 calls/ticker, capped by `massive_tech_max_tickers`) scored as the `massive` method, run ALONGSIDE our own `tech` for a head-to-head comparison. Tracked + persisted to the `signals` panel + trade attribution (dashboard Entry Performance labels it **"Massive Tech (RSI+MACD)"**), and PROMOTED into the weighted `combined_score` (2026-06-24 — `massive` weight 0.15 in `_BASE_WEIGHTS` + `active_flags` + combine + coherence). A weighted method must score EVERY ticker (else capped-out tickers reserve its weight in the normalised pool and get dampened), so `massive_tech_max_tickers` now defaults to **0 (uncapped)** — revert by re-capping AND removing `massive` from the combine together. `enable_massive_tech` (default on).
3F. Fundamentals overlay    — Massive/Polygon financials & ratios (TTM P/E, P/B, EV/EBITDA, ROE, ROA, D/E, dividend yield, market cap) per ticker (`src/data/fundamentals.py` → `polygon_client.get_ratios_batch`, daily-cached, batched via `ticker.any_of`). NOT a scorer — passed into the synthesis prompt as a `<fundamentals_context>` quality/valuation OVERLAY (instruction §28; a conviction/horizon modifier, never a standalone trigger). ### Data flow design
```

**Two tiers of data:**
- **Per-ticker signals** (news, sentiment velocity, technical, trend strength, insider): scored `[-1.0, +1.0]`, combined in `aggregator.py` with configurable weights into a `TickerSignal`. News sentiment is the *level*; sentiment velocity is the *rate of change* (Δ recent−prior tone) — distinct methods, distinct weights. Trend strength (ADX/DMI + Donchian) measures trend *quality* and is distinct from price momentum (return *size*). Convergence multiplier — a continuous `coherence_factor` ∈ [0.45, 1.35] (magnitude-weighted fraction of active methods agreeing with the combined direction, mapped linearly; replaced the old binary 1.25×/0.60× toggle) — dampens confidence when methods disagree. **Cross-family agreement + tape confirmation (2026-07-19, `src/signals/agreement.py`):** the flat `sources_agreeing` count treats correlated methods as independent voters (the OHLCV technicals all read the same tape — pseudo-replication), so `METHOD_FAMILIES` rolls the 21 weighted methods into 7 independent INFORMATION families (Sentiment / Price-Trend / Rel-Strength / Volume-Flow / Options / Smart-Money / Event-Arb; drift-tested vs `_BASE_WEIGHTS`); per-family magnitude-weighted votes (real `family_vote_threshold` 0.05 — no hairline-0.01 "agreement") are counted at the FAMILY level against the combined direction, exposed per ticker to the synthesis prompt (sighted arm: `FAMILY AGREEMENT: N aligned, M opposing — Sentiment:+0.42|…` + instruction to weigh cross-family above same-family pile-ons; blind arm: neutral `FAMILY ROLLUP` only, no verdict leak), folded into confidence via a breadth-of-independent-confirmation factor ∈ [1±`family_agreement_factor_span` 0.12] (1 family alone → neutral 1.0; an opposing family drags 1.5× as hard as an aligned one helps), and stamped on new trades (`families_at_entry`). Win-rate-filtered methods are excluded from votes; INVERTED methods vote with their corrected sign. **Tape confirmation** (`enable_tape_confirmation`) is the SCORE-INDEPENDENT half: a raw price/volume state composite from the cached daily OHLCV (20d range position + up/down-day volume share over 10 bars + last-bar RVOL signed by its direction → ∈ [-1,+1], + = bullish structure; cache-only, NaN/zero-guarded, cold cache → NO_DATA neutral) that qualifies agreement rather than joining the combine: confidence × `1 + 0.08×(tape × direction)`, a per-ticker `TAPE STRUCTURE` prompt line, and panel persistence as the `fam_net`/`tape` pseudo-methods (scores JSON + long-format sim rows) so their forward IC is monitored like any method. `enable_family_agreement`/`enable_tape_confirmation` default ON. Tests: `tests/test_family_agreement.py`. **Score-sign convention** (the invariant the combine, IC, and inversion all depend on — see the `aggregator.py` module docstring): EVERY method's score sign is the predicted direction of the STOCK (`+` = up/bullish, `−` = down/bearish, position-independent), and mean-reversion/contrarian methods bake the reversal INTO the sign rather than reporting state; `|score|` = confidence. **Weighting stack** (all multiplicative, then normalised across active methods): hand-set `_BASE_WEIGHTS` placeholders → market-mode profile → **win-rate adaptive** (`enable_adaptive_weights`, default ON — tilts by each method's solo win rate from the *trade ledger*, Bayesian-shrunk) → **IC-informed adaptive** (`enable_ic_weights`, default **ON but CONFIDENCE-GATED** — tilts by each method's reliability-adjusted IC = ICIR over the *unbiased signals panel*, but ONLY for methods whose IC clears a statistical-confidence gate: the mean-daily-IC t-stat `|ICIR|·√n_days ≥ ic_weight_min_t` (default 2.0 ≈ 95%). A method below the gate keeps its base weight; a confident method is boosted `clip(ICIR / median(confident positive ICIR), min, max)` (typical confident method → 1.0×); a confidently anti-predictive one is floored to `ic_weight_min_multiplier` until it is added to the **`inverted_methods`** switch. **Automatic method inversion (2026-07-25, `enable_auto_inversion` default ON, `tracker.calibrate_method_inversion`).** Inversion used to be a hand-edited `.env` string, and an inverted method got a BLANKET exemption from the win-rate filter — so nothing ever verified that flipping it produced a better-than-chance method; an inversion could hold full weight indefinitely on the strength of the raw record that justified flipping it. Now TWO bars must both clear before a method is auto-inverted: (1) its gross solo win rate is significantly below 50% by a one-sided EXACT binomial (`math.comb`, not a normal approximation — the decision permanently sign-flips a live signal) at a **PLAIN, UNCORRECTED** `inversion_alpha` (0.05) on that method's full history, **and the finding REPLICATES on the independent panel arm** (`inversion_require_replication`, default ON — see below for why replication replaced the multiple-comparison correction); and (2) **the FLIPPED view must itself clear `winrate_filter_threshold`** — ties (`exit == entry`) count as losses on BOTH sides, so `flipped ≠ 100 − raw` (`_tie_share` measures the gap), and a mostly-tied method can be significantly bad raw AND still sub-50% flipped: that is NOISE, not backwards information, and is left for the ordinary filter to drop. Evidence floor `inversion_min_trades` (30, deliberately higher than the filter's 10 — inverting claims more than dropping). Candidates are `_BASE_WEIGHTS ∪ INVERTIBLE_OVERLAYS` only (inverting something the combine never reads is a no-op dressed as a decision). **Inversion is strictly PER-METHOD, never per-FAMILY**: a family (`agreement.METHOD_FAMILIES` — Sentiment / Price-Trend / Rel-Strength / Volume-Flow / Options / Smart-Money / Event-Arb) is a grouping used for BREADTH VOTING, not a signal with a sign, so it has nothing to invert — family votes simply read each member's already-corrected EFFECTIVE sign, so inverting `insider` fixes its vote inside Smart-Money while leaving `broker_advisor` untouched. No family name collides with a method name (asserted in `tests/test_auto_inversion.py`). An unrecognised entry in `inverted_methods` — a family name, or a TYPO — used to be parsed and then silently do nothing, which in the typo case silently UN-inverts a live method; `_manual_inverted_methods` now warns once per bad name (with a family-specific hint) and the name stays inert. **The win-rate filter now judges EVERY method — inverted included — on its EFFECTIVE (inversion-corrected) win rate** (`compute_solo_method_gross_winrate(effective=True)`), replacing the exemption: an inverted method stays only while its corrected record clears 50%. **PINS RETIRED 2026-07-26 — inversion is now FULLY AUTOMATED (`INVERTED_METHODS=` empty).** The three manual pins (`insider`, `market_momentum`, `cross_sectional`) were each contradicted by the unbiased panel arm and have been removed; the detector alone decides, and it currently selects NOTHING. Consequence, measured before the change: all three fall to the win-rate filter instead of being inverted (raw win rates 44.0% / 39.6% / 40.8%), so they now contribute 0 rather than working in reverse — **9 of 21 pool methods dropped, 12 surviving, book verified still producing two-sided directional views**. Retiring `cross_sectional` required closing a gap first: the filter iterated `_BASE_WEIGHTS` only, so an OVERLAY could never be dropped however bad its record — un-inverting it would have PROMOTED it from backwards to full 0.20 weight with no protection, strictly worse than either state. The filter now judges `_BASE_WEIGHTS ∪ INVERTIBLE_OVERLAYS`, and `aggregator._overlay_factor(method)` carries BOTH decisions for an overlay (0.0 when filtered, ±1.0 otherwise — filter beats inversion, since a method bad on both sides is noise rather than backwards information; fail-soft so a broken lookup never silently zeroes a live weight). Panel-first methods (weight 0) stay out of the filter's candidate set — filtering something that contributes nothing is meaningless. Manual `inverted_methods` pins remain SUPPORTED and are UNIONED in and always win (the human override, and how a sub-bar inversion stays live); auto-detection is fail-soft so a broken detector can never silently un-invert a live method. **Arm B — the signals PANEL (2026-07-25, `tracker.panel_inversion_evidence`, `enable_inversion_panel_arm`).** The ledger arm is starved (~150 attributed trades), so this reads the `simulated_trades` panel — tens of thousands of solo directional calls — through `compute_directional_perf`, already the documented market-relative (net-of-beta) inversion readout. A method qualifying on EITHER arm is inverted. **The shared-decay control is the design, not a refinement:** measured 2026-07-25, the share of methods with negative ICIR runs 35% @30m → 61% @1d → **76% @2w → 79% @1m**, while `combined_score` ITSELF runs −0.227 @1d to **−2.187 @2w**. That is the system's holding-period edge decay (the effect the edge-decay time-stop exists for), shared by everything — so testing a method's ICIR against ZERO at a long horizon flags almost the whole book while measuring only how long positions are held, not whether a signal points backwards. Each method is therefore scored on its **EXCESS over `combined_score` at the same horizon**, and only at horizons matching the real holding period (`inversion_panel_horizons`, default `1d,3d` — median hold ~1.3 days, measured edge peak 1–2d). Must be negative at EVERY horizon with |t| = |excess|·√signal-days ≥ `inversion_panel_min_t` plus a multi-comparison bump. Cached 6h (`inversion_panel_cache_seconds`) — the join is expensive and the panel moves in days, not ticks; abstains entirely if the `combined_score` yardstick is missing (no control ⇒ no verdict). **FIRST READ 2026-07-25: the panel arm qualifies NOTHING, and it CONTRADICTS all three live pins** — at 1d/3d excess, `insider` is **+0.301/+0.447** and `cross_sectional` **+0.052/−0.155**, i.e. at or better than system average; the most negative is `market_momentum` (−0.290/−0.283) at t 1.39/1.30 against a 4.43 bar. The pins are human overrides and are NOT auto-removed, but nothing in the unbiased panel currently supports them. Tests: `tests/test_panel_inversion_arm.py`. **Why there is NO multiple-comparison correction (2026-07-26).** There genuinely are ~13 tests per run, so it looks like a Bonferroni setting — but a correction computed from the COUNT of tests is indefensible here, because the tests are not independent: over 246,396 scored ticker-days the six methods that clear the plain ledger test correlate at **+0.72 mean pairwise Spearman**, with `momentum` vs `market_momentum` at **0.98** — the same signal measured twice. Bonferroni assumes independence and so over-corrects, dividing α by 13 when the effective number of independent tests is nearer 2–3 (it selected NOTHING at all); plain α has the exact mirror flaw, reporting six "findings" that are one phenomenon counted six times (expected false positives at α=0.05 with 13 coin-flip methods is only 0.7, so six hits is real — but it is ONE real thing: the trend-following family did badly in this sample). No α setting distinguishes those cases, because the test count is not the right denominator. **Replication replaces it:** one plain per-method test on full history, which must then reproduce on the panel arm — different data, ~1000× the observations, a different statistic, its own shared-decay control. Six correlated ledger hits that fail to reproduce are one unconfirmed phenomenon, handled by construction rather than by arithmetic. It is also the only safeguard that touches the multiplicity α-correction never addressed: we re-evaluate EVERY RUN (~28×/day), so a method parked near the boundary crosses it eventually by chance. Replication is symmetric — a panel finding the ledger never flagged is not two pieces of evidence either. **LIVE 2026-07-26: six methods clear the plain ledger test (`market_momentum` p=0.0055 … `tech` p=0.0165) and NONE reproduce on the panel, so nothing is inverted** — the same outcome the discarded Bonferroni produced, now for a reason that is auditable instead of arbitrary. Reported to the calibration registry as `auto_inversion`. **FIRST READ 2026-07-25: NOTHING clears the corrected bar** — 13 methods judged ⇒ α = 0.05/13 = 0.0038, and the best candidate is `market_momentum` at p = 0.0055 (`sector_momentum`/`trend_strength`/`cross_sectional` 0.009, `momentum` 0.014, `tech` 0.016, `insider` 0.114). So all three live inversions are MANUAL PINS below the automatic bar — each does clear bar 2 comfortably (corrected: `market_momentum` 59.7%, `cross_sectional` 58.6%, `insider` 55.2%), and `insider`'s original justification was market-neutral ICIR across horizons over the whole signals panel, a much larger evidence base than the 116 attributed trades this test sees. Tests: `tests/test_auto_inversion.py`.

**Method inversion (`inverted_methods`, `INVERTED_METHODS` in .env, `aggregator._inverted_methods`):** a method whose RAW score is reliably anti-predictive NET OF BETA across horizons (confirm via `python -m src.analysis.scorecard` or `simulated_trades --directional` — a side whose market-relative ICIR is confidently negative and STAYS negative across horizons) is SIGN-FLIPPED in the combine (its weight is negated) and lifted off the IC floor to base weight — a reliably-backwards signal, corrected, is a reliably-right one. The signals panel keeps the RAW score so the inversion stays re-validatable (raw IC still backwards ⇒ keep it; flips positive ⇒ remove it); `coherence_factor`/`sources_agreeing` read each method's RAW (pre-inversion) score when checking agreement with the combined direction — a documented, accepted inconsistency for an inverted method (its raw score is typically the OPPOSITE of what's actually driving combined_score, so it can read as "disagreeing" even when it's the correct explanation). The newer cross-family agreement (`family_factor`, below) does NOT share this quirk — it votes on each method's EFFECTIVE/corrected sign, so it and coherence can legitimately disagree on the same ticker. **2026-07-08: `insider` AND `market_momentum` are both inverted** (live `INVERTED_METHODS=insider,market_momentum`; each measured reliably anti-predictive net of beta across horizons — insider's market-neutral ICIR is negative at EVERY horizon, −0.11 @30m → −2.26 @1w; `market_momentum` is a weighted method at 0.08 in the Rel-Strength family). So on a thin panel NOTHING clears the gate ⇒ pure no-op — it is safe to run live now and reweights method-by-method as each matures. `_ic_weight_multipliers`/`_ic_mults_from_ic_table`, cached `ic_weight_cache_seconds`; the better-founded successor to the ledger-based layer) → OpEx max-pain boost → extended-session overlay. **Scorer-version epochs (2026-07-24, `src/signals/method_epochs.py`).** Method scores are persisted on every trade (`trades.method_scores`) and every scored ticker (the `signals` panel), and then fed back into LIVE decisions — the win-rate filters, the adaptive tilt, the IC-weight layer. When a scorer is FIXED, all of that stored history was produced by a function that no longer exists, so judging the new implementation on it is simply wrong (2026-07-24: all 235 closed `money_flow`-attributed trades carried scores from a version that could not express direction at all; at a few trades/day a blended win rate would have kept the FIXED scorer suppressed for months on the BROKEN one's record). `METHOD_SCORER_EPOCH` maps a method → the UTC INSTANT its current implementation went live (a datetime, not a date — a deploy lands mid-session, and five trades entered earlier that same day would otherwise have counted as evidence for the new scorer); `score_is_comparable(method, when)` gates `compute_solo_method_gross_winrate` + `_hypothetical_trades_for_method` (so both the win-rate filters and the adaptive-weight tilt honour it), and `epoch_for(method)` gives date-granular consumers — `signal_panel.compute_ic`, hence the IC-weight layer — the day AFTER a mid-day change so the ambiguous partial day is excluded rather than half-admitted. Fail-OPEN: no epoch, or an unparseable timestamp, means comparable, so a malformed date can never erase a method's whole history. **The mask is applied CENTRALLY in `signal_panel.build_panel`** — the single entry point every `signals`-table analysis goes through (predictability, horizon_edge, policy_eval, scorecard, source_performance, confidence_components, price_volume_perf, the IC table) — so a NEW analysis is protected by default rather than having to remember the registry; superseded values become NaN, which every consumer already treats as "no view", while the ROW is kept because its forward returns, prices and unchanged method columns remain valid evidence. **A second, independent choke point does the same job for the SEPARATE `simulated_trades` table** (`analysis/simulated_trades.load_sim_trades` → `_drop_superseded_scorer_rows`): that table is long-format (one row = one method's single directional call, written live by the pipeline every tick — `pipeline.py` around the recommendations-persist step — and read by `compute_method_perf`, which feeds the dashboard's "All scored tickers (simulated)" toggle, explicitly labeled "unbiased ... thousands of observations"), so a superseded row is DROPPED outright rather than column-masked — there is nothing else on the row to preserve. Found and fixed 2026-07-24 in the same sweep that added the registry: this table had NO protection until then, and `money_flow`'s 154,727 pre-fix rows (98% of its 157,438) were sitting in exactly the surface the dashboard frames as the unbiased ground truth. **`compute_macro_eval`'s category-bundle rows are the third, more diluted path** (the dashboard's Macro Evaluation table's "Bundle · <category>" rows, e.g. "Technical" = 21 summed methods including `money_flow`): a member's score is excluded from its category's Σ at rows dated before that member's epoch, so a superseded implementation's history can't tilt the bundle's direction — diluted 1-of-N rather than the isolated per-method exposure the other two paths carry, but not zero. **Register categorical changes only** (the output MEANS something different), not refinements: `money_flow` qualifies (it went from unable to express direction to direction-aware); the 2026-07-22 combine change (pooled → buy−sell, measured a wash at IC5 −0.037 vs −0.041) and the 2026-07-19 confidence factors (bounded ±12%/±8%) do NOT — registering them would blank 86% and 75% of the panel for no gain. **Deleting the superseded rows outright (from `signals`) was considered and rejected on the same arithmetic**: money_flow's stale scores alone are 96.5% of the 276k-row panel, so a literal "remove data from machinery no longer in use" rule would destroy most of a five-week forward-collected asset the IC-weight, predictability-sizing, edge-decay and policy-eval layers all depend on — and would take each row's still-valid parts with it. Residual gap: `analysis/data_quality.load_signal_rows` reads `signals` directly and is DELIBERATELY unmasked — it measures whether a feed is ALIVE (any non-zero score), not whether the score is correct, so masking there would misreport a fixed-but-formerly-buggy method as a feed that "went dark". Tests: `tests/test_method_epochs.py`, `tests/test_simulated_trades.py`. Effect: a freshly-fixed scorer falls below `winrate_filter_min_trades` and therefore keeps FULL weight — "unproven", not "disproven" — and re-earns its place on evidence its own code produced. **Whenever you change what a scorer OUTPUTS (not merely refactor it), add the instant here.**

**Replay — regenerate the evidence instead of discarding it (2026-07-27, `src/analysis/replay.py`).** The epoch mask above achieves comparability by THROWING AWAY evidence; replay achieves the same comparability by REGENERATING it, and is strictly better wherever it is faithful. It is faithful for the OHLCV-derived methods. Measured over the FULL materialised panel — **293,237 ticker-days, 1,803 tickers, 842 runs, joined run-exact** — rescoring history with the current scorers reproduces the stored value with a **median error of 0.0000**: iv_rank 86.3% exact, trend_strength 82.5%, momentum 82.1%, tech 82.0%, vwap 75.4%. **Fidelity decays with age, so always quote the span**: `tech` reproduces at **97.7%** over the last two days versus 82.0% over the full five weeks (the residue is the retroactively split-adjusted cache plus per-ticker start dates shifting the series-length-dependent normalisations). **This supersedes the earlier "only ~62% reproducible, so no retrofit" claim, which was measured with the wrong truncation and was the sole basis for that refusal.** Truncation is the entire game: `bars <= signal_date` scores ~30% exact (the live pipeline DROPS the still-forming bar, so an intraday run never saw that day's bar), `bars < signal_date` ~68%, and only the **time-aware** rule — each row's own `generated_at` decides, the signal-date bar existing solely for a run at/after the 16:00 ET close (`replay.visible_history`, mirroring `market_data._drop_forming_bar`) — reaches 92%. Getting it wrong does not look like a bug; it looks like history being unreproducible. **The decisive validation is a natural experiment**, `money_flow` (scorer fixed 2026-07-25) against `tech` (unchanged) as the control, over the whole panel: **pre-epoch money_flow 1.1% vs tech 81.0% (n=276,454); post-epoch money_flow 93.1% vs tech 97.7% (n=16,783)**. The control holds in both buckets while money_flow diverges only before its epoch — i.e. the divergence is the scorer change being correctly detected, and the replay regenerates precisely the 276k rows the mask was dropping. **Always carry an unchanged control through a reconstruction check**: it is what separates "the scorer changed" from "the replay is broken", and it is also what caught the run-join bug below. **The JOIN must be run-exact, and this is the subtler half**: `signals` holds ~43 runs per ticker-day and `build_panel` keeps one, so joining a replayed value on (date, ticker) alone grafts an arbitrary run's score onto the panel's row — measured to change **56.8%** of `tech` values (a scorer that never changed) versus **2.3%** run-exact. `restore_replayed` keys on `generated_at`; the tell was the control moving when it had no reason to. **Restore-before-mask**: `build_panel` overwrites replayable superseded scores from the materialised `signals_replay` table, and the epoch mask then skips those cells (`enable_panel_replay_restore`) — a restored cell holds the CURRENT scorer's semantics, so blanking it by its original date would silently undo the restore and leave the panel where it started (that ordering is the regression `tests/test_replay.py` pins, verified to fail against un-fixed code). Materialised by EOD maintenance (`enable_eod_replay_refresh`, `eod_replay_refresh_days` 45) or `python -m src.analysis.replay --write`; `--validate` prints the fidelity table and should be run after ANY scorer change. **Scope is a claim about faithfulness, not about inputs** (`schema.REPLAYABLE_METHOD_COLUMNS` = tech, vwap, momentum, money_flow, trend_strength, iv_rank): `pattern` is EXCLUDED despite being OHLCV-driven because it blends a live accuracy registry that grows with every trade (replaying it today uses a registry the original run never saw — 44% exact), and `sector_momentum` because its second leg is a sector ETF fetched at CURRENT time; everything else (news, sentiment, the options family, insider, pead, massive) needs a point-in-time feed nobody stored and can never be replayed — for those the mask remains the only correct answer. **VALIDATED 2026-07-28 (`--validate`, plus a restore-on/off panel diff).** Coverage 300,207 of 304,184 ticker-days (**98.1%**); the restore leaves the panel's ROW SET identical (13,691 → 13,691 — values only), every restored value inside [-1,1], zero inf. **The IC diff doubles as the look-ahead test**: a leak would show as uniform IC improvement, and instead the five UNCHANGED scorers move by ±0.02 in BOTH directions (tech −0.0034, vwap −0.0210, momentum +0.0089, trend_strength +0.0170, iv_rank −0.0078) — the fingerprint of ~15% of values being slightly different reconstructions, not of future information. The payoff is `money_flow`: **0 usable observations at 5d/10d → 10,120 / 7,233** (1,402 → 13,521 overall, **9.6×**), IC −0.0073/−0.0420/−0.0500, i.e. squarely in the normal band rather than a suspicious spike. **No-look-ahead is enforced by three adversarial probes** (`tests/test_replay.py`), not by inspection: appending 60 EXTREME future bars leaves every score bit-identical; every method still scores with `get_history`/`load_ohlcv` patched to RAISE (each scorer has a fetch path guarded by `if df is None` — the probe proves the guard, since a silent fallback would price a past date with today's data); and no bar past `signal_date` is ever visible in either run type. **The split guard** (`_scale_is_consistent`, `_SPLIT_GUARD_LO/HI` 0.67/1.5 — tighter than `tracker`'s 0.5/2.0 because that one protects a RETURN from a fabricated ratio and need only catch ≥2×, while this protects SCORE fidelity and should reject any rescaling; observed snapshot-vs-close noise is 0.92–1.06) refuses the ~0.20% of rows (496, 26 tickers) whose cache was rescaled after the fact — the one genuinely future-facing input, since the unadjusted history was never stored. Those rows do reproduce badly (tech 36.3% exact vs 87.9%), which is what confirms the detector finds the right ones. Because the per-row check needs a live price and **13.8% of rows have none**, a per-ticker **cutoff** propagates the finding: a split contaminates only the dates BEFORE it, so earlier priceless rows on a flagged ticker are suppressed while clean post-split history is kept (banning whole tickers would drop 3,893 rows to fix 179). **Residual, unmeasurable by construction:** a ticker that split and has NO priced row anywhere in the panel leaves no trace to detect.

**Recovered MARKET CONDITIONS (2026-07-28, `schema.REPLAYABLE_CONTEXT_COLUMNS`).** The claim that confidence "cannot be reproduced" was too broad — the same over-broad refusal as the 62% one. Every market-condition INPUT is recoverable, because it comes from the same cached OHLCV as the method scores: `atr_pct`/`bb_width_pct`/`vol_ratio` are fields of the very `compute_technical_score` result that yields the `tech` score (they were being computed inside the replay and DISCARDED), and `tape_score` is the cache-only tape composite. **`movement_factor` is the one confidence component that does NOT depend on the weights** — `_movement_factor(atr_pct, bb_width_pct)` × a dealer-gamma modifier — so it is genuinely RESTORED (**21.3% → 98.4%** of panel rows; measured 91.8% exact against the captured values). Its one approximation is GEX, which is options data and unreplayable: a bounded 0.85/1.15 multiplier that is 1.0 unless dealer gamma is PINNED/AMPLIFIED, preferred over NaN precisely because it is bounded. The other four columns are ADDED, never having been persisted at all (0 → ~94.5%), so they cannot perturb an existing analysis — an absent column is absent to every consumer. **The other five components stay masked at 21.3% and that is the correct outcome, not a shortfall**: each takes `combined_score` (hence the weights) as an input, so recomputing them is a BACKTEST, not a recovery. Two gotchas, both regression-tested: `compute_tape_confirmation` loads the cache ITSELF unless handed `df=`, so omitting it would have read today's full history while pricing a past date — a silent look-ahead inside the very feature being added; and the CONFIDENCE mask needed the same skip-restored-cells fix the scorer mask already had, or `movement_factor` would have been re-blanked and the work made a no-op (verified to fail against un-fixed code). Perf: `compute_technical_score` was running TWICE per row (3.33 ms of 22.1 — ~15% of a materialisation); now computed once and shared, pinned by a drift test asserting the shared object still yields exactly what `_score_one` produces.

**Series-integrity guard — the SECOND split detector (2026-07-28, `_series_is_intact`, `_MAX_PLAUSIBLE_ATR_PCT` 1.0).** `_scale_is_consistent` needs a live-recorded price, so a ticker with NO priced row anywhere in the panel is invisible to it — this was documented as an unmeasurable residual until the recovered `atr_pct` exposed it: **ADTX, a serial reverse-splitter with NaN price on all 7 rows, replayed at atr_pct 108.0**. It IS measurable through a second channel, because a split leaves a fingerprint in the bars: ATR averages true range over price, so exceeding the price requires a discontinuity. Distribution over 302k replayed rows is unambiguous — median 0.0387, p99 0.157, p99.9 0.524, then a jump to 108.0 — so the bound sits at 1.0 (~2× beyond p99.9) and rejects **139 rows (0.046%) over 8 tickers**; max `atr_pct` post-guard is 0.939. A discontinuous series invalidates the SCORES as much as the context, so the whole row is skipped. Fail-open when there is no `atr_pct` to judge. **Generalisable lesson: when one detector needs an input that is sometimes missing, look for a second fingerprint of the same event in a different channel rather than accepting the gap.**

**Walk-forward calibration — weights as production would have had them (2026-07-28, `src/analysis/asof.py` + `walkforward.py`, table `weight_history`).** A backtest applying TODAY's weights to ALL history measures a configuration that could not have existed: those weights were fitted on data that, relative to any historical row, is the FUTURE. Measured here, that is not a technicality — the book genuinely ran **18 active methods on 2026-06-24, 15 on 06-26, 12 by 06-27 and 10 from 07-02** (the market-relative filter cannot drop a method until it has ≥200 observations), so a fixed-weight backtest misstates the early period wholesale. **`analysis_asof(date)`** installs a point-in-time cutoff honoured at the same three choke points the epoch mask uses — `signal_panel._load_signals`, `simulated_trades.load_sim_*`, `tracker._load_trades` — so the entire weighting stack recomputes seeing only strictly-earlier rows. **The ledger filter keys on the EXIT, not the entry**: a trade entered before the cutoff but closed after it carries a realised return that had not happened yet, so admitting it on its entry date would leak exactly the outcome a win-rate calibration is trying to predict; open trades are excluded entirely (no outcome to contribute). **The caches are the trap and the reason this is a module rather than a WHERE clause**: every layer memoises on a TTL, NOT on the cutoff (`_IC_WEIGHT_CACHE`, `_WINRATE_FILTER_CACHE`, `_SIDE_SKILL_CACHE`, the panel memo, market-relative, method-horizons, four in `tracker`), so without an explicit flush step two of a walk silently reuses step one's weights and the whole run collapses into ONE calibration wearing a walk-forward label — a failure that looks exactly like success. `analysis_asof` flushes on entry AND exit (exit because point-in-time calibrations must not leak into live decisions). `walkforward.materialize` stores one row per step in `weight_history` (weights, inversions, global + per-side filters, per-side multipliers), reading every layer through the aggregator's own helpers so it cannot drift into a private copy of the weighting stack. `backtest.run_backtest(walk_forward=True)` is now the DEFAULT and resolves the weight set per signal date via `weights_for_date` — the latest calibration **strictly before** it (a same-day calibration saw that day's own data); a row predating every calibration is **SKIPPED**, never backfilled with today's weights, since that would reintroduce precisely the look-ahead this removes. Rows are stamped `wf:<as_of>` instead of a global hash so each is auditable. Measured 2026-07-28 over 266k rows: walk-forward is closer to what actually ran than the fixed-weight backtest on both metrics (36.1% vs 34.9% direction agreement, 12.0% vs 14.7% flat contradictions), and the two backtests agree 84.5% overall but only **60.3% in the early period** — the fixed-weight error localised exactly where the weight histories differ. Kept current incrementally by EOD maintenance (`enable_eod_walkforward`, `walkforward_eod_days` 3 — a step is a fixed fact once its data is in, and each costs ~60s, so only the tail is rewalked). **This is also what would dissolve the tier-2 firewall**: the ban exists because weights fitted on the whole panel and applied back to it is self-confirmation, and under a cutoff weights at D cannot encode D's outcome. The firewall is deliberately still IN PLACE pending end-to-end validation of the walk-forward path — the argument is sound, the implementation is new. Tests: `tests/test_walkforward.py` (the cache-flush test verified to FAIL against un-flushed code).

**AUTOMATIC database refactor (2026-07-29, `src/analysis/code_version.py` + `refactor.py`, tables `code_versions` / `refactor_runs`, `enable_auto_refactor`).** The standing rule was that stored history must reflect the current implementation; the ENFORCEMENT was a docstring asking whoever changed a scorer to hand-edit `METHOD_SCORER_EPOCH` — correct only while someone remembered, which is the exact class of safeguard this project keeps finding broken. It is now mechanical. **Detection:** every method maps to the module(s) computing it (`METHOD_SOURCES`, all 42 mapped — `unmapped_methods()` must stay empty and a test asserts it, since an unmapped method opts out of refactor SILENTLY), fingerprinted by **normalised AST** rather than source text: comments, blank lines, formatting and docstrings do NOT move the fingerprint, a changed constant or reordered branch DOES. Verified both ways against a live scorer — editing a constant in `money_flow` fired and was classified `regenerate`; adding a docstring, a comment and a blank line to the same file fired nothing. Methods with no module of their own (`max_pain`, `oi_skew`, `market_momentum`, `insider`) are scored inline in the aggregator and map to it — coarse but correct, since an edit there really can move them. **Repair runs in DEPENDENCY ORDER, and that is the part that cannot be got wrong:** (1) DATA — regenerate replayable scores via `replay`; (2) EPOCHS — for what cannot be regenerated, the epoch is DERIVED from `code_versions.first_seen_at`, no hand-edited registry; (3) WEIGHTS — re-walk `walkforward`, which must follow the data because weights are FITTED on it; (4) DERIVED — `backtest`, which depends on both. Reversing any pair yields a database that looks refreshed and is internally inconsistent (weights fitted on scores that no longer exist), which is strictly worse than one that is visibly stale. **The replayable/non-replayable asymmetry governs the risk posture:** a replayable method is REGENERATED, so a false positive costs only CPU and the detector can be liberal; a non-replayable one can only be MASKED, which withholds real history, so those are reported and masking is opt-in (`refactor_auto_epoch`, default **OFF**) — a cosmetic edit to a sentiment module must not silently blank 78% of the panel, and the detector cannot tell cosmetic from categorical. **Fingerprints advance only on FULL success**: recording them after a partial failure would mark the database consistent with code it was never refactored against, so the next run would see no changes and the staleness would become permanent AND invisible; a failed step keeps the old fingerprint, retries next EOD, and alerts. First-run baseline is distinguished from a change (`is_new`) so a fresh database does not read as "42 scorers changed". Wired into EOD after the walk-forward; on an unchanged day it costs one AST hash per method. CLI `python -m src.analysis.refactor --check|--apply`. Tests: `tests/test_refactor.py`, `tests/test_code_version.py`.

**The one genuine limitation is circularity, and it applies only to DERIVED values:** method scores do not depend on the weights, so replaying them and calibrating weights from the result is sound; `combined_score`/`confidence`/gate outcomes DO depend on the weights, so replaying those with today's weights is a BACKTEST — legitimate to inspect, invalid to re-calibrate those same weights from. `signals` is never overwritten: it records what actually happened and stays the audit trail. Tests: `tests/test_replay.py`, `tests/test_method_epochs.py`.

**Significance tests are dependency-free by rule (2026-07-27, `src/analysis/stats.py`).** `method_horizons` and `regime_performance` each called `scipy.stats` inside `try/except Exception` falling back to a neutral verdict — but scipy was never a declared dependency and was not installed, so **the except branch was the only branch that ever ran**: every method classified UNPROVEN (never PROVEN, never DISPROVEN, silently feeding live method weighting) and every regime comparison reported "test unavailable". A degraded verdict is indistinguishable from a real one. Exact binomial (`binom_p_less`/`binom_p_greater`, log-space so large n cannot overflow) and Welch's t-test (`welch_t_test`, via a regularized incomplete beta) now live in-tree, verified against exact integer arithmetic and a textbook example, and the call sites **deliberately do not wrap them in a bare except** — a genuine failure must surface. Degenerate input returns NaN ("no verdict"), never 0.0 ("certainly different"). `tests/test_stats.py` pins the arithmetic and asserts neither module reimports scipy. **General rule: an optional import guarding a verdict the system ACTS on is an invisible off switch, not a graceful fallback.**

**Silent channels — the same defect class, mechanised (2026-07-28, `tests/test_inert_settings.py::test_no_module_logs_into_a_silent_channel`).** The scipy fallback above was one instance; the second surfaced within the hour. The project configures **loguru** sinks ONLY, so `logger = logging.getLogger(__name__)` anywhere in `src/` yields a logger with no handler and every `.info()`/`.warning()` on it is DISCARDED. Eight modules had it (`replay`, `arm_eval`, `arm_shadow`, `market_relative`, `method_horizons`, `regime_history`, `regime_performance`, `ticker_performance`), which muted `replay`'s skip counts and — the reason it matters — the deliberately-raised fail-soft WARNING that distinguishes "the restore is broken" from "the table isn't populated yet". Worse than an unread setting, because the entire purpose of those lines is to make a degraded path audible. All eight converted to `from loguru import logger` and a test now scans `src/` so it cannot recur. **The unifying rule for all three (unread setting, unreachable import branch, sinkless logger): a mechanism whose failure mode is INDISTINGUISHABLE FROM NORMAL OPERATION must be verified mechanically, never by review.**
**Stream-separation invariant (2026-07-25 audit).** The per-side filter must reach **coherence, `sources_agreeing` AND family agreement**, not just the combine — `aggregator` applies `_side_ok(method, eff)` when building `method_score_map_eff`, keyed on the METHOD's own effective sign (exactly the test the combine loop makes), so all four see the same book. **Per-SIDE win-rate filter + weighting (2026-07-24, `enable_side_winrate_filter` / `enable_side_adaptive_weights`, both default ON):** a method's bullish and bearish calls are separate skills, and the 2026-07-24 directionality audit measured them far apart over 237 attributed trades — most methods hit ~40% on their BUY-side views and ~47–59% on their SELL-side views (`insider` 37.7/51.9, `iv_rank` 43.9/54.5, `st_reversal` 42.9/64.2). One blended win rate hides that, so with the buy/sell split combine each camp is filtered and weighted on ITS OWN record: `compute_solo_method_gross_winrate(side="buy"|"sell")` restricts the sample to that side's views; `aggregator.side_filtered_methods(side)` drops a method from ONE camp when its win rate on that side is `< winrate_filter_threshold` over `≥ winrate_filter_min_trades` **side** views (same exemptions as the global filter — inverted methods never dropped, thin samples keep full weight); `side_weight_multipliers(side)` then scales each survivor's weight within that camp by its demonstrated side skill, Bayesian-shrunk toward 50% by `side_weight_prior_n` (10) and clamped to `side_weight_min/max_multiplier` (0.5–2.0) — the same idiom as the blended adaptive layer. **Guard:** the per-side filter is suppressed for a camp it would EMPTY — an always-zero camp makes the buy−sell difference fall one way on every ticker, turning the book structurally single-direction, a far larger bet than a filter should place (logged as a warning; mirrors the global filter's never-empty-the-book guard). Live net effect beyond the global filter: `news` + `iv_rank` dropped from the bullish camp only (their short calls are kept and weighted UP), `pattern` dropped from the bearish camp only. **Bug fixed the same day in the shared path:** `rec.get("win_rate", 50.0) or 50.0` silently rewrote a genuine **0.0%** win rate as 50% (0.0 is falsy) — so the worst possible method escaped the filter AND received a neutral 1.0× weight; all three call sites now use the None-checked `aggregator._win_rate_pct`. Tests: `tests/test_side_winrate_filter.py`.
**Per-method HORIZON SKILL — three states (2026-07-26, `src/analysis/method_horizons.py`, `enable_method_horizons`).** Measured over the SOLO-METHOD simulation (`simulated_trades`) gated at `buy_sell_diff_threshold` — the gate a single method driving `combined_score` would really face — giving **~1,500–3,300 observations per method against the trade ledger's 78–174**, the difference between "cannot tell" and an answer. **A method is not good or bad; it is good over a particular HOLDING PERIOD.** Judged at 1 day only, exactly ONE method cleared p<0.05 and the book would have collapsed to a single signal; judged across 1/3/5/10 days FIVE clear, with coherent shapes: `sent_velocity` 52.4% @1d (p=.003) then decays — the expected profile for a RATE-OF-CHANGE signal; `pattern` builds monotonically to 52.8% and clears at BOTH 5d (p=.015) and 10d (p=.025); `iv_rank` 52.1% @5d (p=.017); `iv_expr` 56.6% @3d (p=.040); `oi_skew` 57.7% @10d (p=.048). Three states: **PROVEN** (significant >50% at some horizon) keeps full weight; **DISPROVEN** (significantly <50% at EVERY judgeable horizon — currently only `market_momentum`) is dropped by the filter; **UNPROVEN** (the other 12) is scaled by `unproven_weight_multiplier` (0.5) rather than zeroed — absence of evidence is not evidence of absence, and zeroing the middle would collapse the ensemble that coherence, `sources_agreeing`, family agreement and Gate 1b all require. Multiple comparisons across the four horizons are NOT alpha-corrected, for the same reason as the cross-method case: the horizons are CORRELATED (a 3-day return contains the 1-day one), so the guard is profile **coherence** — an edge that builds monotonically or clears at two adjacent horizons is credible (`pattern`, `iv_rank`, `oi_skew`), a lone spike surrounded by noise is flagged (`sent_velocity`, `iv_expr`). **This basis SUPERSEDES the trade-ledger filter when available** (`aggregator.horizon_disproven_methods`), because the ledger is selection-biased — it holds only calls that survived every gate, which is how `vwap` measured **58.0% (p=.020, n=174) there and 50.2% (p=.431, n=2,692) here on 15× the data**: its apparent edge was selection, not signal. CLI `python -m src.analysis.method_horizons`. Tests: `tests/test_method_horizons.py`.

**`method_horizon` EXIT signal (2026-07-26, `exit_methods.method_horizon_days`).** A position's target hold is the CONVICTION-WEIGHTED average of its own methods' measured best horizons (`|method score| × |base weight|` at entry, PROVEN methods only), so a `sent_velocity`-driven trade is stale after ~1 day while a `pattern`-driven one still has ~5 to run; a trade driven entirely by unproven methods gets NO deadline rather than a fabricated one. Emitted as the `method_horizon` exit score (0 inside the window, increasingly negative past it, bounded to −1) and it **PARTICIPATES in `exit_method_consensus`** — deliberately unlike the other two time-stops: `horizon` is skipped because it reflects the LLM's stated target and `edge_decay` because it is one global window measured on `combined_score`, whereas this one is built FROM the methods that opened the position and so is a method view. It ADDS to the existing exit stack (macro / flip / confidence-loss / trailing / mechanical / horizon / edge-decay), replacing none of them.

**Market-relative WEIGHTING (2026-07-27, `src/analysis/market_relative.py`, `enable_market_relative_weighting` default ON).** An ABSOLUTE win rate cannot separate "this signal works" from "the market went up": measured on 296k ticker-days, a low-volatility screen won **53.5% at 5 days and only 46.1% net of SPY** — the entire apparent edge was beta. The per-side adaptive weighting (`_side_skill` → `side_weight_multipliers`) therefore reads MARKET-RELATIVE hit rates from `compute_directional_perf` (thousands of observations per method — 246 to 5,929 — versus the ledger's 78–174), falling back to the absolute ledger basis whenever the panel is unavailable, so the change can only add information. **The neutral point is the MEASURED baseline, not 50%** (`_measure_baseline`, observation-weighted across the panel, currently **≈48.1–48.6%**): the cap-weighted index beats its typical constituent, so the median stock is market-relative-NEGATIVE, and centring the shrinkage on 0.5 would hold every method to a bar ~1.4pp too high and read ordinary methods as weak. A half-migrated basis — relative numerator against a 50% bar — is worse than either pure basis. **Scope is deliberate:** weighting and inversion (which already preferred market-relative ICIR) use this basis because they are SIGNAL-QUALITY decisions where beta is a confound; the hard filter, sizing, the edge blend and all P&L reporting stay ABSOLUTE, because the book is outright long/short and alpha it cannot capture must not size it. **The HARD FILTER also uses this basis** (`enable_market_relative_filter`, 2026-07-27): a method whose calls do not beat the benchmark in the direction called is not adding information however well the absolute number reads in a rising market. Bar is a literal 50% (`winrate_filter_threshold`) — on this basis the median stock is market-relative-NEGATIVE, so 50% is the STRICTER of the two defensible bars and the deliberate risk posture; `market_relative_filter_baseline=true` switches to the measured ~48.1% bar, and the two differ ONLY by the methods sitting between them (currently `ext_gap` 49.7% and `insider` 49.2%). Observation floor is `market_relative_min_obs` (200) — unproven is not disproven — inverted methods stay exempt, and **every dropped method is still scored, persisted to the `signals` panel and IC-tracked**, so it can re-earn its place. LIVE EFFECT: this takes the dropped set from **1 to 12 of 22** — survivors are `vwap`, `iv_rank`, `pattern`, `sent_velocity`, `oi_skew`, `max_pain`, `iv_expr` plus the three thin/exempt methods; the book was verified still producing two-sided directional views. **Re-entrancy bug fixed in the same change:** the auto-inversion detector's bar 2 asks for the EFFECTIVE (inversion-corrected) win rate, which calls back into `_inverted_methods` — so computing the inverted set depended on already knowing it. Latent before, that chain re-entered **22 times per filter evaluation** once the market-relative filter added another entry point, re-running the panel join each time and blowing the recursion limit inside `simulated_trades`. `_INVERSION_IN_FLIGHT` now returns the MANUAL pins while a computation is in flight — terminating, and semantically right since the detector cannot depend on its own output (8 calls now, no recursion). Surfaced on the dashboard's method table as **Rel win % / vs base / Rel n** beside the absolute Win rate % — shown together rather than swapped, since the GAP between them is exactly the beta the absolute number cannot see (4 of 18 methods change verdict between the two bases, most notably `vwap` at 47.5% absolute vs 51.7% relative). Tests: `tests/test_market_relative_weighting.py`.

**Win-rate HARD filter (`enable_winrate_method_filter`, default ON, `aggregator.winrate_filtered_methods`):** distinct from the soft win-rate tilt above — any `_BASE_WEIGHTS` method whose GROSS solo win rate (`compute_solo_method_gross_winrate` — the PURE directional hit rate `sign(score)·(exit−entry) > 0`, BEFORE fees/spread, so a method is judged on picking the right DIRECTION not on clearing the round-trip cost; ~more lenient than the net `compute_solo_method_performance` basis — e.g. a mean-reversion method whose small right-direction moves get eaten by spread survives) is `< winrate_filter_threshold` (0.50) over `≥ winrate_filter_min_trades` (10) attributed trades is DROPPED from the active pool ENTIRELY: weight → 0 (surviving methods renormalise so the score stays on scale, not merely shrunk like the adaptive floor), excluded from coherence / `sources_agreeing`, AND hidden from the synthesis prompt's per-ticker score lines (`claude_analyst` imports the same cached set) so the LLM never leans on a sub-coin-flip method. INVERTED methods are EXEMPT (their sign is already corrected, so a sub-50% RAW win rate is precisely why they're kept); a method below `min_trades` keeps full weight (small-sample noise ≠ bad method); and `build_signals` suppresses the filter for any run where it would empty the active book (never all-NEUTRAL). The dropped method is STILL scored + persisted to the `signals` panel + trade-attributed every run, so IC / win-rate / simulation monitoring keeps accruing and a filtered method can re-earn its place (or be inverted). Cached `ic_weight_cache_seconds` (build_signals runs many times/tick). Every computed method reaches `combined_score` — EXCEPT the eight PANEL-FIRST methods at weight 0 (`hi52`/`mom_12_1`/`st_reversal` classic anomalies + `squeeze`/`iv_term`/`avwap` Tier-2 + `resid_mom`/`vol_profile` Tier-3; IC-measured + trade-attributed, zero combine/coherence/exit-consensus influence; promotion = a `_BASE_WEIGHTS` entry + combine/coherence lines once their IC clears the gate). **Buy/sell split combine (2026-07-22 user directive, replacing the single normalised pool):** each of the 21 `_BASE_WEIGHTS` methods' inversion-corrected view (`eff`; the weight's sign carries the inversion) is decomposed into a BUY component `max(0, eff)` and a SELL component `max(0, −eff)`, both ∈ [0,1]; each side is weight-averaged over the methods HOLDING that view only (its own camp — abstainers and the opposing camp no longer dilute a side, unlike the old pool where every active method's weight sat in one denominator); `combined_buy_score` = the bullish camp's conviction, `combined_sell_score` = the bearish camp's, and **`combined_score` = their DIFFERENCE**. Direction fires on the difference clearing `buy_sell_diff_threshold` (0.15 — the old band, revalidated on the 11.3k-row panel where the split yields a notably more BALANCED 18%/21% bullish/bearish mix vs the old pool's 32%/15%, countering the measured BUY-output skew; predictive quality old-vs-new was a wash, IC5 −0.037 vs −0.041 — the value is separability + balance). Deliberate consequence: a lone loud bull against many bears reads as a strong buy CAMP — camp SIZE is judged by the machinery built for it (coherence factor, Gate 1b `sources_agreeing`, family agreement), not by re-diluting the score. Both side scores are persisted per ticker (`signals.combined_buy_score`/`combined_sell_score`), ride the sighted synthesis prompt line (`buy_score=`/`sell_score=`; withheld in the blind arm like every aggregate verdict field), and are IC-monitored as the `cmb_buy`/`cmb_sell` rows (sell side sign-negated into the standard convention) — forward-collected from 2026-07-22. Tests: `tests/test_buy_sell_split.py`. (Fewer than 21 methods are actually WEIGHTED on a given run once the win-rate hard filter above excludes any confirmed sub-50% ones.) The 6 corp-action/fundamental `f_*` factors AND the 4 trend-predictability methods (`kaufman_long`/`kaufman_short`/`adx_long`/`adx_short`) are additive overlays OUTSIDE the split (all sparse/one-sided in context) — they land on the DIFFERENCE, exactly as they landed on the old pooled sum. The 4 trend methods are active only in their trend CONTEXT (`*_long` = uptrend, `*_short` = downtrend) and each raw signal is multiplied by a **learned orientation** ∈ [−1,+1] (`trend_predictability.calibrate_trend_orientation`): +1 predicts continuation (keep the trend's sign), −1 predicts reversal (flip — a downtrend-context method then emits a BULLISH score to predict a bounce), magnitude = confidence. The orientation is measured per method from the signals panel (how often that context has continued vs reversed at the swing horizon) shrunk toward a CONTINUATION prior by signal-days, so it starts as continuation and flips toward reversal only as forward returns confirm it (it will learn "clean downtrends bounce → predict up"). Because the orientation carries the direction quality, the overlay uses a single symmetric weight (`trend_method_weight` 0.10).
**Confidence EPOCH + component-capture fix (2026-07-27).** Asked whether the panel could be RETROACTIVELY rescored with the current confidence setup. **Rejected, and this replaced it.** Reasons in order of severity: (1) today's weights are CALIBRATED FROM THIS PANEL, so rescoring the past with them injects future information into the very dataset that feeds the IC-weight layer, predictability sizing and policy eval — the bias would propagate into live sizing and gating, not just a report; (2) **78.3% of rows predate the component capture** (components exist only from 2026-07-21, 63,680 of 293,735 rows); (3) the OHLCV cache is retroactively split-adjusted, so `movement`/`volume`/`tape` cannot be reproduced as they were — the same fact that killed the `money_flow` retrofit at 62% fidelity. **Regime HISTORICAL retrofit (2026-07-27, `src/analysis/regime_history.py`, CLI `python -m src.analysis.regime_history --start 2000-01-01`).** Live history holds only calm days, so PANIC/RISK_OFF/RISK_ON are untested in production — that is an absence of stress, NOT evidence the bands are wrong, and the way to tell them apart is to replay the composite over years that had stress. **Still open — the deeper limit on regime work.** The regime's information lives at LONG horizons and almost vanishes at the one the system trades: the best-to-worst spread is **2.94pp at 21 days but only 0.227pp at 1 day (13×)**, against a **median hold of 1.3 days**. So the regime is a multi-week beta forecast being used to gate 1-day trades, and no amount of regime tuning has much leverage on realised P&L — worth knowing before investing further here. Two further misalignments are measured but deliberately NOT acted on: **NEUTRAL is the weakest non-PANIC state** (+0.37% at 21d, 59.9% up) yet carries the second-loosest gate and is 53% of all days; and the regime is a BETA statement, so it arguably belongs on the **long/short balance** (via the existing per-side thresholds) rather than on a symmetric bar. Caveats throughout: PANIC's 66 days are 55-in-GFC, and `macro_news` — the input most likely to fire earliest in a real crisis — remains unreconstructable.

**Regime validation (2026-07-26, `src/analysis/regime_performance.py`, CLI `python -m src.analysis.regime_performance`).** Does the regime label carry information? ### Performance calculation

Performance numbers come from two engines that work side-by-side, both rooted in the *real* observed prices stored on each trade — never interpolated, never synthesised.

**STANDING RULE — a calibration may only fit data the CURRENT code produced (2026-07-27, user directive).** Fitting on values a superseded implementation produced fits a relationship that no longer exists. Two mechanisms enforce it, and **both must be considered whenever a scorer or the confidence formula changes**:

* **Panel side** — `signal_panel.build_panel` masks superseded method scores (`METHOD_SCORER_EPOCH`) and confidence + its components (`CONFIDENCE_EPOCH`) to NaN. Every panel-reading analysis inherits this for free, which is why the mask lives at that single choke point.
* **Ledger side** — `build_panel` never runs on the trade ledger, so calibrations reading trade fields need an explicit gate: `method_epochs.score_is_comparable` for method scores (already used by the win-rate filter and the adaptive tilt) and **`method_epochs.confidence_is_comparable`** for trade `confidence`, now applied in `calibrate_side_threshold` and `calibrate_confidence_sizing`. Measured when that gate was added: **75% of the closed trades feeding both carried the pre-buy/sell-split confidence scale** (mean 0.873 vs 0.945) — `calibrate_side_threshold` was fitting Spearman(confidence, return) across two scales, and `calibrate_confidence_sizing` was filing rows under confidence BANDS they never belonged to (the 0.07 gap is roughly a band's width). Both fail OPEN on a missing/malformed/non-date-shaped timestamp, so bad data can never silently erase history.

**Excluding, not converting.** The rule is satisfied by RESTRICTING each calibration to comparable data, never by rescoring history onto the current formula — a retrofit was measured and rejected twice (see `METHOD_SCORER_EPOCH` and `CONFIDENCE_EPOCH`), decisively because today's weights are calibrated FROM the panel, so rescoring the past with them would feed future information into the dataset that drives live sizing and gating. Excluding is honest; converting would be invention. **The Bayesian shrinkage every calibration already carries is what makes the smaller clean sample safe** — each goes inert on thin evidence rather than over-fitting it (post-gate the confidence-sizing layer sits at n=71 and is correctly inactive).

**Self-calibrating parameters (2026-07-03).** Frozen constants are being replaced by values learned from the system's own tables, all through one idiom (documented prior → evidence → Bayesian shrinkage → clamps → fail-soft to the static setting) and all REPORTED to the calibration registry (`src/performance/calibration.py` → snapshotted per run into `gate_diag["calibrations"]` → the Data Quality tab's Calibrations table). Current set: per-session real-fill costs (`_one_side_cost` session split; extended/overnight = measured RTH × multipliers shrunk toward the ×4/×10 priors), the derived horizon cost hurdle (`spread.effective_cost_hurdle_pct` = 2 × measured one-way × safety, replacing the static 0.40%), the engine-relative actionable threshold (`analysis/threshold_calibration.py` — regime thresholds translated into the run engine's confidence scale by matching gate selectivity), the calibrated exit-confidence floor (`analysis/exit_floor_calibration.py` — the hold/bleed boundary measured from trade_reviews outcomes), breadth sizing (see record_new_trades), the expected-edge sizing blend (`performance/edge_sizing.py`), and the predictability sizing tilt (`performance/predictability_sizing.py` — trend-efficiency/ADX size tilt whose strength is the panel's high-vs-low directional-hit gap shrunk by signal-days; Tier 1 of the "find easier-to-predict swing names" work, measured by `analysis/predictability.py`), and the edge-decay time-stop window (`analysis/horizon_edge.py` — the realized edge-positive holding window of `combined_score` measured tick-by-tick over the signals panel, evidence-throttled into a raise of the exit confidence-loss floor once a position outlives it). Universe **provenance** is stamped per run (`signals.universe_source` + the same field on trades + per-source counts in gate_diag) so per-source hit rates can drive an adaptive discovery budget once data accrues. Risk guardrails (liquidity floors, exposure caps, wipe guards, order-cap ceilings) and the calibrations' own meta-parameters stay fixed by design.

**Per-trade `return_pct` (buy-and-hold, cost-aware) — `tracker._pct_return()`**

```
cost_in  = _one_side_cost(entry_price, asset_type)            # half-spread + commission
cost_out = _one_side_cost(exit_or_current_price, asset_type)
BUY  : eff_entry = entry × (1 + cost_in);   eff_exit = exit × (1 − cost_out)
       return_pct = (eff_exit − eff_entry) / eff_entry × 100
SELL : eff_entry = entry × (1 − cost_in);   eff_exit = exit × (1 + cost_out)
       return_pct = (eff_entry − eff_exit) / eff_entry × 100
```

**Per-trade cost attribution (2026-07-23, `sim_per_trade_cost_attribution`, default ON).** Layered ON TOP of the flat/session override below, each sim leg is charged the cost that best fits it, by a four-tier hierarchy (`spread.resolve_leg_cost` / `resolve_trade_leg_cost`): (1) the leg's OWN realized cost when it FILLED at the broker — commission + execution-vs-decision slippage from the trade's own `broker_fill_price`/`broker_commission`/`entry_price` fields, sanity-banded (a >±2% "cost" = stale decision price → discarded, falls through); (2) else the average one-way cost of the trades that FILLED in the same tick (run) — the entry leg keys on `trade["run_id"]`, needs ≥`sim_cost_tick_min_legs` (3) fills; (3) else the average for the leg's time-of-day PERIOD (`rth | premarket | afterhours | overnight`, the `_session_of_iso_fine`/`spread.session_bucket_fine` split — needs ≥`session_cost_min_legs` fills); (4) else the modeled/global `_one_side_cost` (which itself still honors the flat/session override + the sub-`sim_real_fill_min_price` model guard). This preserves ledger PURITY — every sim trade still assumes it fills; only the COST charged is sourced more precisely: a filled trade pays what its execution really cost, an unfilled one pays what its peers that tick/period actually paid. Built each tick by `calibrate_sim_costs` from the same sanity-banded fills as the flat override and installed via `spread.set_cost_attribution` (run/period averages + a `client_ref→run` map), so the daily-NAV compound stays deterministic from the DB (the per-run/period averages still drift as later fills land — same property the flat override always had). BOTH return engines resolve costs through the one shared `resolve_trade_leg_cost` (threaded into `_pct_return` via `entry_cost`/`exit_cost` and into `daily_nav._effective_entry/_effective_exit` via `cost=`), so they charge identical per-leg costs — the two-engines-agree invariant. NET EFFECT on the current ledger: MORE conservative (closed-trade compound −8.85% flat → −15.4% attributed) because the flat blend was dominated by cheap, plentiful RTH fills and undercharged the many unfilled off-hours exits (fill rate ~13%), which now correctly pay their period's realized average (overnight ~0.53% / premarket ~0.35% / afterhours ~0.44% vs the 0.184% flat). `false` → the flat/session override for every leg (pre-2026-07-23 behaviour). Tests: `tests/test_per_trade_cost_attribution.py`.

**Short borrow carry (2026-07-25, `enable_short_borrow_cost` / `short_borrow_annual_pct` 3.0%).** The one genuinely direction-ASYMMETRIC cost: a short pays a daily stock-loan fee a long never does, and nothing charged it before — so every short's simulated return read BETTER than reality by roughly rate × holding period, a bias growing with the hold and largest on exactly the squeeze-prone names the (disabled) `broker_advisor` was built to flag. It is a HOLDING cost, so it does NOT go through `_one_side_cost`: `spread.borrow_cost_fraction(action, days, trade)` returns a fraction charged per **calendar** day (borrow accrues over weekends, unlike the trading-day conventions elsewhere) on SELL legs only, subtracted from the return in `_pct_return(borrow_cost=…)` and per-day in the daily-NAV walk so both engines agree. The rate prefers the broker's REAL fee for that name (`trade["borrow_fee_pct"]`, from `Broker.get_short_borrow`) and falls back to the blended setting — the same prefer-measured-over-modelled idiom as the real-fill costs. Measured impact on the current ledger: −0.022 pp per short (small only because the median short is held 1.26 days).

**Direction-scoped parameters (2026-07-25, `config.settings.directional(name, direction)`).** Resolves `{name}_long` / `{name}_short` when set, else the shared `{name}` — the mechanism behind "a parameter set optimised for buying and another for selling", built so a split is a config change rather than a refactor. **Every override defaults to None (inert).** Deliberately NOT applied to every threshold: the 2026-07-25 analysis found the long/short gap in the ledger does NOT survive multiple-comparison correction (permutation p 0.014 → Bonferroni ×8 = 0.111), so hand-setting two values from that sample would fit noise. Splits are justified where the asymmetry is STRUCTURAL, or where a threshold SWEEP is stable across a wide band — never on a single point estimate. Prefer a shrunk per-side calibration (`aggregator.side_weight_multipliers`, `tracker.calibrate_horizon_ramp`) over a frozen pair wherever the quantity can be measured.

**Hard adverse stop (2026-07-25, `enable_adverse_stop`, `adverse_stop_pct_long` 8% / `adverse_stop_pct_short` 20%).** Every other exit is conviction-based, so nothing capped a single position's loss — a position the engine keeps re-affirming could bleed indefinitely. Fires on the cost-adjusted M2M return, and only when the LLM review HELD (like `trailing_stop`/`mechanical_exit`), so it never overrides a macro or flip close; `exit_reason = "adverse_stop"`. **The split runs OPPOSITE to the structural prior, and the measurement is why.** "A short's loss is unbounded, so stop it tighter" is sound about tail risk but wrong about where the tail starts: a threshold sweep over the closed ledger (Δ = capped-at-stop − realised, via each trade's stored MAE) found a stop HELPS longs at every level from −5% to −12% (+2.13 pp/trade at −6%, +1.22 at −8%) and HURTS shorts at every level from −5% to −15% (−2.80 pp/trade at −5%, worsening to −20.87 at −15%) — shorts that go against this book tend to RECOVER, consistent with the earlier finding that SELLs on spiked names fade correctly. Both readings are stable across a wide band rather than a single point, which is what makes them actionable at n=153/88. The short side is set to −20% (a pure runaway guard, where the sweep shows no harm) rather than disabled, because the unbounded-loss tail is still real.

**Per-side actionable threshold (2026-07-25, `tracker.calibrate_side_threshold`, `enable_side_threshold_calibration`).** Gate 1 is the highest-leverage parameter in the system, so this split is deliberately the most conservative of the set: MEASURED (not hand-set), Bayesian-shrunk by `side_threshold_prior_n` (40), capped at `side_threshold_max_adjust` (+0.04 confidence points), and it can **only TIGHTEN** — a negative correlation never lowers the bar, because loosening a risk gate is not something a calibration may do. The evidence is deliberately NOT "which side wins more" but whether confidence **DISCRIMINATES** on that side, since raising a bar only helps if the bar sorts good calls from bad: `Spearman(entry confidence, realised return)` per direction, scaled by `side_threshold_rho_ref` (0.30). Measured 2026-07-25 — **longs +0.011 (no information; the ≥0.90 cohort was the WORST at −2.11%, so the long bar stays at 0.851) and shorts +0.232 (monotonic bands, ≥0.90 the only profitable cohort at +1.91% / 43.6% win → bar raised to 0.871)**. Resolved once per run, applied per recommendation at Gate 1, and surfaced in `gate_diag.threshold_adj_buy/sell` so a run's effective per-side bar is auditable. Pin a side with `actionable_threshold_adj_{long,short}` to skip the calibration. **Tie-handling matters here:** `_spearman_conf_return` delegates to `signal_panel._spearman` (pandas average-tie ranks) — a hand-rolled ranker that breaks ties by input order manufactures correlation, because trades load chronologically and confidence has many ties (an alternating ±5% series scored 0.571 instead of ~0.09 before the fix).

**Per-side horizon ramp (2026-07-25, `tracker.calibrate_horizon_ramp`, `enable_horizon_ramp_calibration`).** `horizon_expiry_floor_mult` is now resolved per DIRECTION and MEASURED rather than hand-set: the evidence is the gap between what `horizon_expired` trades returned and what that side's other exits returned. A NEGATIVE gap means the time-stop let losers bleed → tighten; POSITIVE means patience paid → loosen. Measured 2026-07-25: **longs −1.88 pp (tighten → 1.65), shorts +2.54 pp (loosen → 1.38)** from a shared base of 1.50 — opposite directions, which is exactly what one shared parameter cannot express, and consistent with the adverse-stop finding that longs need decisiveness and shorts patience. Bayesian-shrunk by `horizon_ramp_prior_n` (30) so it is ~inert on thin evidence, clamped to ±`horizon_ramp_max_adjust` (30%), floored at 1.0, cached like the other per-run calibrations, and reported to the registry as `horizon_ramp_long/short`. Tests: `tests/test_directional_params.py`.

The one-way cost (`spread._one_side_cost`) is **half-spread + commission**. Bid-ask half-spread is price-tiered and asset-type-aware (see `_dynamic_half_spread` in `src/performance/spread.py` for the May-2026-calibrated tiers). The commission term (`_commission_fraction`) is a deliberate **fee ceiling, not a best estimate** — results must err conservative: the pricier all-in plan is the default (`ibkr_fixed`: max(\$1.00, \$0.005/share); `ibkr_tiered`: max(\$0.35, \$0.0035/share), commission only; `none`: spread-only), capped at 1% of trade value, then × `commission_buffer` (default **1.5**, applied after the cap) to cover SEC/TAF sell-side fees, venue/clearing fees under tiered, surcharges, and schedule drift — ~41 bp round trip at the assumed `commission_notional_usd` (≈730 USD — a deliberate constant, not live FX, so the math stays deterministic; the 1.0× base notional is also the worst case, since larger positions see a smaller min-commission floor in % terms) vs ~27 bp actual. Unrecognized model names fall back to `ibkr_fixed`, not the cheaper plan. **Real-fill calibration (`sim_use_real_fill_costs`, default on):** once at least `sim_real_fill_costs_min_legs` (default 10) actual **LMT** fills exist, `calibrate_sim_costs()` measures the average all-in one-way cost from them (real commission + execution-vs-decision-price) and installs it through `spread.set_real_cost_override()`. **Sanity band (2026-07-23, `sim_real_fill_cost_sanity_pct`, default 2.0%, 0 = off):** a filled leg whose measured one-way cost lies beyond ±2% is DISCARDED as a bad record before averaging — a capped marketable LMT (20 bp RTH / 80 bp extended / 150 bp overnight) cannot legitimately fill percent-points from its own anchor, so such a leg means the recorded `model_price` was stale, not that execution was brilliant. The plain mean had no defence against them: 17 corrupt legs out of 346 (5%, **all negative**, −2.0% to −7.1% — a one-sided tail real execution noise never produces) pulled the measured one-way cost from 0.185% to **0.0006%**, so the sim was charging ~zero transaction cost on *every* trade (0.0013% round trip vs ~0.37% guarded / ~0.48% modeled) and every reported return was inflated accordingly. **The SAME band is applied to the per-SESSION split** in `calibrate_sim_costs` (the `by_session` overrides): without it the all-negative outliers dragged each session mean below zero → clamped to 0 → since `_one_side_cost` consults the session override BEFORE the flat one, it returned **zero cost for every leg on the session path** — a broad latent zeroing (the flat-fraction fix alone did not cover it). Post-fix the split reads rth ~0.10% / extended ~0.29% / overnight ~0.72%, matching the ×4/×10 priors. NOTE the residual, unfixed bias: the sample is drawn only from legs that FILLED, and the fill-or-kill regime fills ~13% of LMT orders — systematically the easy ones — so even the guarded figure understates the cost of the *intended* trade population. The sim's purity contract is "assume every trade fills", not "assume fills are free"; if that bias matters, floor the override at the modeled cost (`max(measured, modeled)`), which also restores the documented err-conservative principle as a **flat per-leg cost that REPLACES the modeled half-spread + commission** for every leg — so the sim charges what execution actually costs, not the estimate. **Source is LMT-only** (`repo.fetch_filled_lmt_legs` → `broker_orders WHERE order_type='LMT'`, ENTRY/EXIT, drift-flatten cleanups excluded): MKT fills are deliberately ignored because LMT is what the system uses going forward (the old uncapped-MKT fills — e.g. −107 bp ZUMZ — would otherwise inflate the basis). Below the floor (or when disabled) it falls back to the model; the override is clamped ≥ 0. The pipeline calls it before the tick's normalize/M2M/entry steps and `get_performance_for_email` before its NAV walk, so a run uses one cost basis throughout (the process-global override is reset per-test by conftest). This supersedes hand-tuning `commission_buffer` — the buffer now only matters before enough LMT fills accumulate. At this system's order sizes the commission minimum dominates spread on liquid large caps. Closed trades use `exit_price`; open trades use the live `current_price` (refreshed each tick by `update_open_trades()`, timestamped via `current_price_datetime`). For open trades this is a "what if you closed right now" mark — same convention as the email's M2M display. `_normalize_closed_returns()` recomputes this each pipeline tick from the stored entry/exit prices so every closed trade's `return_pct` reflects the current cost model.

**Path-faithful daily compound — `daily_nav.compute_compound_return(trades)`**

Per-trade walk:
1. Load OHLCV closes for the ticker from `cache/ohlcv/<TICKER>.json` (force-refreshed for open-trade tickers via `tracker._refresh_open_trade_ohlcv()` so today−1's close exists).
2. Build chronological marks: `(entry_date, eff_entry)` → every cached close strictly between → `(exit_date or today, eff_exit)`. The entry/exit anchors apply the same `_one_side_cost` (half-spread + commission) as `_pct_return`, so both engines charge identical costs; intermediate marks are raw closes, **no cost applied** — those days the position is marked-to-market, not traded.
3. For each adjacent pair compute `r_d = sign × (mark_d − mark_{d−1}) / mark_{d−1}` with `sign = +1` for BUY, `−1` for SELL. The short formula is path-faithful (depends on adjacent days only), not the buy-and-hold formula — so a volatile short's daily compound legitimately differs from its `return_pct` (volatility decay for daily-rebalanced shorts).

Portfolio aggregation:
1. Collect every `(date, daily_return, weight)` tuple from every trade (`weight = position_size_multiplier`).
2. Group by date; per-day portfolio return = `sum(r·w) / sum(w)` over active positions.
3. Compound sequentially: `compound = ∏(1 + day_return) − 1`.

This is **deterministic given the database**: same DuckDB (`data/llm_trader.db`) + same `cache/ohlcv/*.json` produces bit-identical output. The real-fill cost calibration (above) does not break this — the override is a pure function of the broker fills stored in that same DuckDB, so identical inputs still give identical costs (it just reads one more table). Time-window variants (`return_1w`/`return_2w`/`return_1m`) just filter trades by `entry_date >= today − N days` before aggregating; the cost basis is always derived from the FULL ledger so it stays stable across the dashboard's window/session toggles.

**Hypothetical solo & eval stats — `tracker._flip_trade()` / `_hypothetical_trades_for_method()`**

For "what if only this method had decided" simulations:
- If the method's sign matches the actual trade's action → use the trade verbatim (real walk, real `return_pct`).
- If it disagrees → `_flip_trade()` returns a same-ticker/same-dates trade dict with `action`/`direction` inverted and `return_pct` re-derived via `_pct_return` for the flipped action. The daily-NAV engine then walks the **real OHLCV closes** in the opposite direction — no negation-of-stored-number tricks.

Conviction bands (`_eval_stats`): Low `0.10–0.35`, Medium `0.35–0.65`, High `0.65+` on `|method_score|`. Each band reports `trades`, `accuracy` (% with `return_pct > 0`), `avg_return`, and `compound_return` (also via the daily-walked engine). A well-calibrated method shows rising accuracy Low → Medium → High.

### Database (DuckDB)

`data/llm_trader.db` is the **single source of truth** for trades, recommendations, and run history — it replaces the old `cache/trades.json` / `cache/hypothetical_trades.json` ledgers (now import-only). All access goes through `src/db/`:

- **`connection.py`** — `connect(read_only=False)` yields a short-lived DuckDB handle and closes it on exit. Read-write opens `ensure_schema()` first; read-only opens require the file to already exist (raise `FileNotFoundError` otherwise).
- **`schema.py`** — idempotent `CREATE TABLE IF NOT EXISTS` for ten tables: `runs`, `run_sources`, `recommendations`, `trades`, `hypothetical_trades`, `broker_reconciles`, `broker_orders`, `signals`, `trade_reviews`, `arm_recommendations` (every synthesis prompt arm's call on every ticker — see the shadow-arm section). Each trade / hypothetical row stores the **full dict in a JSON `data` column** (so `tracker.py` round-trips byte-identical dicts, exactly as the old JSON files did) alongside projected scalar columns used for SQL and the dashboard. New tables appear automatically on the next write connection; new *columns* on an existing table need a one-time `ALTER TABLE`.
- **`trade_reviews` table (fix #2 confidence trajectory)** — append-only, one row per held position re-judged each tick by the opener-pinned hold-review (`repo.insert_trade_reviews`, written from `pipeline._persist_trade_reviews`): `reviewed_at`, `ticker`, `position_id`, the review's `confidence`/`action`/`direction`, the `conf_floor` it was tested against (`tracker._confidence_floor`), the position's `entry_confidence`/`entry_action`, current `price`/`return_pct`, and the pinned `synthesis_model`/`sentiment_model`. This is the same-engine, apples-to-apples confidence-over-time series the dashboard plots (Recommendations tab → click a row) to see whether conviction deterioration precedes a direction change.
- **`signals` table (the learning panel)** — every run persists the FULL per-ticker signal cross-section (one row per scored ticker, not just the top-10 recommendations): all 19 method scores as DOUBLE columns (mirroring `tracker._ALL_METHODS` via `schema.SIGNAL_METHOD_COLUMNS` — a drift test keeps them in sync) plus `combined_score`, the buy/sell split sides `combined_buy_score`/`combined_sell_score` (2026-07-22, `schema.SIGNAL_COMBINED_SIDE_COLUMNS` — the two camp convictions whose difference is `combined_score`; evaluated in the IC table as the sign-normalised `cmb_buy`/`cmb_sell` rows), `confidence`, `direction`, `n_methods_agreeing`, `dominant_method`, snapshot `price`, and the full score dict as JSON. Purpose: the trade ledger only teaches what the gates let through (selection bias); this panel, joined against forward returns from `cache/ohlcv/`, is the unbiased dataset for information-coefficient analysis and threshold/weight tuning. News/options inputs can't be reconstructed historically, so forward collection is the only path to a backtest-quality dataset. Analyse with `python -m src.analysis.signal_panel` (`--horizons 1,5,10 --days 90`): dedupes to the last run per (day, ticker), computes per-method Spearman IC + directional hit rate per horizon (zero scores = "no view" excluded, `--min-n` floor before an IC is reported), **plus the IC's confidence — `icstd`/`icir`** (stdev & information-ratio of the PER-DAY IC via `periodic_ic_stats`: a Spearman IC is taken within each signal-day, then std/mean across days, so each day counts once and the figure isn't inflated by same-day cross-sectional correlation the way a standard error off the raw stock-day `n` would be; gated by `--min-per-day`/`--min-days`, so it populates only after several signal-days accrue). **IC is computed from the OHLCV CACHE close at `signal_date + h` (not `signals.price`)** — so the forward-return join silently returns `n=0` if the cache lacks the forward bar (e.g. the last tick ran pre-close and `_drop_forming_bar` dropped the forming bar, and no post-close tick cached the completed one). The **`--refresh` flag** (`refresh_panel_ohlcv`) force-warms OHLCV for every panel ticker first so forward returns exist regardless of cache state; a healthy scheduler with a post-16:00 tick keeps the cache warm so `--refresh` is only the offline backstop. **The IC dataset is forward-collected — judge nothing until weeks of cross-sections accumulate** (a single day's IC is regime noise). **Score-inversion readout:** `python -m src.analysis.simulated_trades --directional` prints the per-`(method, side)` MARKET-RELATIVE skill (`compute_directional_perf`, net of `horizon_market_benchmark`, the shadow-curve basis) WITH `icstd`/`icir` — a side whose market-relative ICIR is confidently NEGATIVE (≲ −0.5) and stays negative across horizons is reliably anti-predictive net of beta ⇒ invert that side; an ICIR ≈ 0 is noise, not an inversion signal. Prefer this market-neutral ICIR over the edge-basis (absolute-return) IC for the flip decision — the edge IC can be fooled by drift, and the edge/shadow curves already auto-flip on measured IC/skill sign internally, so a manual inversion only matters for the static `combined_score`/scorer logic.
- **`repo.py`** — the typed read/write API: `load_trades()` / `save_trades()` (full-replace, matching the old whole-file rewrite semantics), `insert_run()`, `insert_run_sources()`, `insert_recommendations()`, and `fetch_df()` (DataFrame reads for the dashboard). `set_read_only(True)` flips every read path to open read-only — the dashboard sets this so it never takes the write lock.
- **`migrate.py`** — one-time `python -m src.db.migrate` imports the legacy JSON ledgers; idempotent (skips populated tables unless `--force`). As a safety net, `tracker._load_trades()` self-seeds the DB from `cache/trades.json` if the DB is empty, so the cutover never loses history even if migration is skipped.

**Concurrency model:** DuckDB allows a single read-write handle OR many read-only handles across processes. The pipeline is the **sole writer** and holds the write lock only momentarily (open → write → close); at the end of every run it persists `runs` + `run_sources` + `recommendations` (`pipeline.py`, wrapped in try/except so a DB hiccup never aborts the run). The dashboard connects **read-only** and retries with exponential backoff across the brief window the writer holds the lock.

Two same-day hotspot fixes underpin this: `tracker._build_pseudo_trades` now derives its `(iso_date, close)` index once per TICKER instead of per call (21.7M datetime conversions removed; `performance` 56.4 s → 18.5 s) with `bisect`/dict anchor lookups, and `cache.load_ohlcv` memoises the parsed frame on (path, mtime, size) returning a **copy** — copy ≈30 µs vs parse ≈1.8 ms, and copy-on-return preserves the reason it was deliberately uncached before (callers like `market_data.get_history` mutate the frame). NOTE two rewrites were measured and rejected: JSON→Parquet for the OHLCV cache saves only ~3 s of a ~60 s sweep (cProfile's 18.6 s for `read_json` was profiler overhead; the real full-universe parse is ~5.7 s), and a different web framework wouldn't help at all since the warm render of the whole 428 KB tree is 0.7 s and the cost was always the Python analytics. **DuckDB push-down (2026-07-24, `simulated_trades.load_sim_entry_events`):** `simulated_method_perf` was ~30 s because `load_sim_trades` pulled **5.27M rows** into pandas and `extract_entry_events` deduped them there; that dedupe is exactly a `lag()` window over (ticker, method) ordered by `generated_at`, so it now runs in SQL — **5.27M rows → 156k entry events, 97% never leave the database** (extraction 10.5 s → 1.34 s; the accessor 30.4 s → 18.3 s, with `compute_method_perf` output verified byte-identical to the pandas path). The scorer-epoch filter is a WHERE clause so it still applies BEFORE the window (dropping rows first is what makes "the previous call" mean the previous COMPARABLE one); it falls back to the pandas path on any SQL error, and an explicit `sim_df=` or a non-`events` dedupe still uses pandas — which is what the ~30 tests stubbing `_intraday_series` depend on. `_fwd_intraday` also stopped rebuilding the ticker's epoch-ns index and re-parsing the timestamp on every one of 148,935 calls (optional pre-computed args, signature kept backward-compatible). **Shared-OHLCV ceiling (2026-07-24, sweep 113 s → 93 s):** after the push-down no single accessor was the bottleneck — the floor is the ~1,760-ticker OHLCV sweep every panel shares. `exit_panel._accumulate` was still calling `_fwd_intraday` on the slow path (69,900 calls) and now passes the pre-computed `times`/`entry_ns`; `_intraday_series` was vectorised (`DatetimeIndex.asi8` + a numpy mask instead of a per-row `pd.Timestamp(ts).value` — **16.4× faster, 0 mismatches over 150 tickers / 170,795 bars**); and decisively the parse memo was **thrashing** — an entry cap of 1500 against a ~3,520-file working set (1,760 tickers × daily + 30-min) meant each panel re-parsed what the previous had evicted. An entry cap is the wrong bound (30-min frames ~54 KB vs daily ~8 KB), so it is now bounded in BYTES via **`ohlcv_parse_cache_mb`** (default 160 MB; measured working set 116.6 MB / 3,538 entries; 0 disables). Result: `shadow_exit_method_perf` 22.8 → **12.5 s**, `performance` 17.1 → 12.7 s, `predictability` 13.9 → 12.4 s, sweep **93.5 s** (confirmed twice), shadow-panel output verified byte-identical. Check `cache.ohlcv_parse_cache_stats()` before optimising an individual accessor — cache sizing beat two algorithmic fixes combined. **Panel memo + SQL dedupe (2026-07-24, sweep 93 s → 77 s):** profiling by SELF time showed `build_panel` was called **9× per sweep with 6 identical** (`horizons=(1,5,10), days=None, dedupe=last`) — ~19 s rebuilding the same 12,289×82 frame because every consumer (predictability, price_volume_perf, horizon_edge, policy_eval, source_performance, confidence_components) built its own. It is now memoised per (horizons, days, dedupe) against the latest `run_id` and hands out COPIES (25.8 MB panel, **4.5 ms to copy vs 6.14 s to rebuild — 1,355×**; bounded to 4 entries, `reset_panel_cache()` in conftest, an explicit `signals_df=` is never cached, and the copy means a caller mutating its panel can't corrupt the shared one). `_load_signals` also pushes the dedupe into DuckDB — `row_number() OVER (PARTITION BY signal_date, ticker ORDER BY generated_at DESC) = 1` instead of `sort_values().groupby().tail(1)`, so **96 % of the 275k rows never cross into Python** (output verified identical; falls back to pandas on any SQL error). **DuckDB is exhausted here:** what remains is the OHLCV forward-return loops (JSON files, not the DB) and pandas internals spread thin — `simulated_method_perf` 18.2 s, `performance` 13.1 s, `shadow_exit_method_perf` 12.4 s, `price_volume_perf` 12.1 s, `predictability` 10.5 s; `exit_panel.extract_activation_events` is the same `lag()` pattern but runs on pandas-RESHAPED frames rather than a raw table, so it has no clean SQL twin. ### Model routing

| Task | Engines (A/B-routed) | Last resort |
|---|---|---|
| Per-ticker sentiment scoring | **DeepSeek V4-Flash 90% / Qwen 10%**, flipped ONCE PER RUN (`sentiment_qwen_share`, default 0.10 — Qwen is pricier, so it scores a minority of runs; the non-primary engine is the per-call error fallback). Claude/Haiku reserved for synthesis and stripped entirely unless `enable_claude_sentiment=true`, which restores the Haiku ⇄ DeepSeek A/B ahead of the Qwen split. | score 0.0 (`none`) |
| Final synthesis / BUY/SELL/HOLD/WATCH | `ANALYST_MODEL` Claude (default: `claude-haiku-4-5-20251001`) ⇄ DeepSeek V4-Flash (`deepseek-v4-flash`) | rule-based `_fallback_recommendations()` |

**A/B routing (`LLM_AB_ANTHROPIC_SHARE`, default 0.5):** each run flips a coin per role — synthesis and sentiment independently — to pick which provider goes FIRST; the other stays as the error fallback (credits exhausted, rate limit, connection failure, missing key). 0.5 gives both engines comparable recommendation samples for the dashboard's per-LLM evaluation rows; 1.0 = always-Anthropic-first (legacy behavior), 0.0 = always-DeepSeek-first. The engine that actually answered is recorded per run (`runs.llm_synthesis_provider` / `llm_sentiment_provider`), per recommendation (`recommendations.llm_provider` — exact model id on new rows; legacy rows hold the provider string), and stamped on each new trade (`llm_synthesis_model` / `llm_sentiment_model`).

**Synthesis N-way bake-off (`LLM_AB_SYNTHESIS_MODELS`, SYNTHESIS only):** when set to a comma-separated list of model ids, the per-run *synthesis* engine is picked UNIFORMLY from that pool (equal split) instead of the binary `LLM_AB_ANTHROPIC_SHARE` flip — so 3+ models accumulate comparable samples and each shows as its own row in the dashboard's per-LLM evaluation (it keys by exact model id). The chosen model's provider is inferred (`_engine_of`: `deepseek*` → DeepSeek, else Anthropic) and `_call_claude_analyst(prompt, model=...)` / `_call_deepseek_analyst(prompt, model=…, thinking=…)` runs it; the OTHER provider's default model is the error fallback (`_synthesis_attempts_for`). **DeepSeek arms encode thinking with a `-thinking` suffix** on a *logical* id (`_deepseek_spec` decodes `deepseek-v4-pro-thinking` → API model `deepseek-v4-pro` + thinking ON); the logical id is what's recorded for provenance (so each variant is a distinct dashboard row), and the stream consumes only `delta.content` so reasoning tokens are billed-but-discarded. Currently (2026-07-22) `deepseek-v4-flash,qwen/qwen3.7-plus-thinking` (≈50% each) — consolidated onto ONE DeepSeek model after the bake-off found the arms statistically indistinguishable: **eleven paired tests** (same ticker, same day, so window/regime is controlled) returned **zero significant differences**, and the models disagreed on direction **0–6 times out of 25–170** shared calls — three pairs disagreed on nothing at all. Engine choice is therefore a cost/latency decision, not an accuracy one. Dropped `deepseek-v4-pro-thinking` (+233s per tick, ~3× tokens, repeats tickers in 26% of its responses) and `deepseek-v4-flash-thinking` (97.6% same-direction agreement with plain flash). Qwen moved `qwen3.7-max` → `qwen3.7-plus`: identical capability on this route (reasoning, response_format, seed, 1M ctx, 65K out) at **~4.6× cheaper input / ~3.5× cheaper output**. NOTE the earlier unpaired tables made Qwen look best and pro-thinking look broken — both were pure window artifacts (Qwen ran 4 days, DeepSeek 23), which is why only the paired comparison is trusted here. The cross-engine error fallback stays cheap flash **non**-thinking. Empty → legacy binary behavior. **Sentiment is separate and CLAUDE-FREE by default, but not DeepSeek-only** — `enable_claude_sentiment=false` (default) removes Claude entirely (not as the A/B primary, not as a fallback, and not via a hold-review engine pin — a `force_engine="anthropic"` pin coerces to deepseek), leaving a per-RUN **90% DeepSeek-flash / 10% Qwen** split (`sentiment_qwen_share` 0.10; measured 90.5/9.5 over 3,000 flips), each engine the other's per-call error fallback. Set `enable_claude_sentiment=true` to restore the Haiku ⇄ DeepSeek 2-way via `LLM_AB_ANTHROPIC_SHARE`, which takes precedence over the Qwen split. (Opus / thinking / pro on per-ticker sentiment would be wasteful on the high-volume cost driver.) The engine try-order is `sentiment._sentiment_engine_order`.

**Synthesis-prompt arms — dual-case / blind / sighted (2026-07-25, `dual_case_synthesis_share` 0.5 + `blind_synthesis_share` 0.5).** Three arms, not four: the dual-case flip is taken FIRST and **supersedes** the blind/sighted axis when it fires (a symmetric two-case presentation is inherently verdict-free), so runs split ~50% dual / ~25% blind / ~25% sighted instead of fragmenting into four cells. The arm is stamped in `gate_diag.dual_case_synthesis` alongside `blind_synthesis`. **Dual-case** presents each ticker as `BULL CASE conviction=… | BEAR CASE conviction=…` — the two camps' SEPARATE convictions (`combined_buy_score` / `combined_sell_score`), each averaged over only the methods holding that view — with NO `direction=` / `combined_confidence` verdict, and instructions that treat "which case does the evidence support" as the question, make a CONTESTED (two similar convictions) or both-weak read an explicit HOLD/WATCH, and state that declining a direction is a correct output. **The substantive fix is the per-method gate:** the per-side win-rate filter gives the two camps DIFFERENT valid method sets (`news` and `iv_rank` are currently out of the bullish camp), but the prompt filtered methods GLOBALLY only — so the model saw `news` while considering a BUY, on a method the system had already decided must not inform buying. In the dual-case arm each per-method line is gated by the side its OWN score points to (inversion-corrected, exactly the test the combine and coherence make): a **bullish** `news` score is hidden while a **bearish** one is still shown, since news's sell side is kept. The other two arms deliberately do NOT apply it — there the model picks the direction after seeing the evidence, so hiding a method by whichever side it happens to point today would be wrong; the global sub-50% filter still applies unconditionally in all three. **Evidence and honest expectations:** the blind A/B moved the echo rate only 94.5% → 91.4%, i.e. the model echoes because it reads the same method scores, NOT because it sees the verdict — so do NOT expect this to change direction-picking much, and the blind-vs-sighted outcome difference was a wash (−2.69% vs −2.56%). What it protects is the cohort where the LLM demonstrably adds value: splitting recommendations by where the direction came from and controlling for side, **echo BUYs returned −3.19% / 33.0% win (n=4,698) while NEUTRAL-ORIGIN BUYs — the aggregator had no view and the model supplied the direction — returned +0.21% / 66.0% (n=150)**; genuine overrides (n=34) won 67.6%. A single-direction prompt would have eliminated exactly those cohorts, which is why that option was rejected. Tests: `tests/test_dual_case_synthesis.py`.

**Shadow synthesis arms — per-ticker arm bake-off (2026-07-25, `enable_shadow_arms` default ON).** The three prompt arms were only observable on the runs where their coin came up, so they were compared over DIFFERENT ticker-days — precisely the unpaired design that made Qwen look best and pro-thinking look broken in the 2026-07-22 model bake-off (both pure calendar artifacts; every difference vanished under paired testing). Fixed by asking EVERY arm about EVERY ticker each tick: the live arm's recommendations drive the run, and the other two are re-asked as **shadow calls nobody acts on** (`src/analysis/arm_shadow.py` → `ShadowArmBranch`, started right after the live recs + provenance capture, joined at persist time so orders NEVER wait on it). Shadow calls are pinned (`force_engine`) to the engine the live arm used, so the ARM is the only difference — and pinning is also what suppresses the run/sentiment provenance writes, so a shadow can never mis-stamp the run (same guarantee the pinned hold-review relies on). Cost: two extra SYNTHESIS calls per tick (synthesis is ONE call for the whole top-N ticker set, unlike per-ticker sentiment, the real cost driver). Fail-soft throughout: a failing arm is skipped, an empty result records nothing rather than a fabricated call, and a join overrun (`shadow_arms_join_timeout_seconds`, 300) persists the live arm alone. Persisted to `arm_recommendations` (run/arm/live/ticker/action/direction/confidence/snap_price, idempotent per run). **Evaluation — `src/analysis/arm_eval.py`** (CLI `python -m src.analysis.arm_eval [--horizons 1,5,10] [--days N]`, dashboard Entry Performance tab): a per-arm summary (action mix, **strategy return** treating a decline as 0 — the dual arm is explicitly told declining is valid, so scoring only its directional calls would hide what it was built for — plus directional-only return/win, and the arm's own confidence IC) and, the row that actually matters, a **head-to-head table measured ONLY over the ticker-days where two arms took DIFFERENT sides**: a shared call is not evidence about either arm, so a high agree % means most of the raw comparison is noise about a shared decision. Treat a Disagree count in the low tens as "no answer yet". The **ledger-side** view is `compute_synth_arm_eval` → "Entry eval · prompt arm DUAL-CASE/BLIND/SIGHTED" rows, stamped `entry_synth_arm` on new trades — this SUPERSEDES `compute_blind_synthesis_eval`, whose boolean OFF bucket silently merges dual with sighted now that the dual arm also sets `blind_synthesis=False` (the old rows are kept for the pre-dual history). Tests: `tests/test_arm_shadow.py`, `tests/test_arm_eval.py`.

**Held-positions prompt A/B (`OPEN_POSITIONS_PROMPT_SHARE`, default 0.5):** a second independent per-run coin flip (pipeline Step 4.6) decides whether the synthesis prompt includes `<open_positions_context>` + instruction §27 — the system's current holdings (direction, entry, last mark, days held) with a zero-endowment-bias review instruction ("judge each held ticker as a fresh candidate; an actionable counter-direction call closes it; confirm or contradict the held direction in the rationale"). OFF runs keep the LLM blind to holdings (the pre-experiment behavior). The flip lands in `gate_diag` (`hold_prompt_active`) and is stamped as `exit_hold_prompt` on every trade CLOSED that run by BOTH close paths (`close_trades_on_signal_reversal` + `monitor_open_positions` — all closes are stamped so second-order effects are captured, e.g. a reversal close today preempting a decay close tomorrow). `compute_hold_prompt_eval()` groups closed-trade outcomes by the flag and the dashboard's method-evaluation table shows the running comparison as highlighted "Exit eval · hold-prompt ON/OFF" rows — once the samples accumulate, set the share to 1.0 or 0.0 accordingly. Tests: `tests/test_hold_prompt.py`.

**Claude API calls use streaming** (`client.messages.stream`) to avoid SDK timeout errors on large prompts (40+ tickers can take >10 minutes non-streaming). Text chunks are accumulated into a single string before JSON parsing.

**Per-model sampling / thinking gating** (`_anthropic_sampling_kwargs` / `_anthropic_thinking_kwargs` in `claude_analyst.py`): newer Anthropic models changed the request surface, so the synthesis call adapts to `ANALYST_MODEL`. **Opus 4.7+ and the Fable/Mythos 5 families REMOVED `temperature`/`top_p`/`top_k`** — sending `temperature` returns a 400 ("temperature is deprecated for this model"), so it's sent (`temperature=0`, for determinism) ONLY on models that still accept it (Haiku 4.5 / Sonnet 4.6 / Opus 4.6 / older) and omitted otherwise. **Adaptive thinking** (`thinking={"type":"adaptive"}`, `display` default `omitted` since only the answer text is consumed) is enabled on the models that support it (Opus 4.6+, Sonnet 4.6+, Fable/Mythos 5) for better BUY/SELL reasoning, omitted on those that don't (Haiku 4.5/older 400 on it). Opus `max_tokens` is 64 000 (thinking tokens count against it). Both helpers are version-aware/forward-looking; an unforeseen sampling-removed model still degrades safely via the engine fallback. Tradeoff: adaptive thinking is non-deterministic, so on a thinking model the fix #2 hold-review re-judgments are noisier than the old temperature=0 path.

**Engine fallback** (`_call_claude_analyst()` / `_call_deepseek_analyst()` in `claude_analyst.py`): whichever engine the A/B flip did NOT pick first is tried automatically when the primary fails — any `anthropic.APIStatusError` (HTTP 400/401/402/403/429/5xx — covers credits exhausted, bad key, payment required, rate limit, server errors), `anthropic.APIConnectionError`, or DeepSeek/OpenAI-SDK error. Both engines receive the identical prompt (DeepSeek via the OpenAI-compatible streaming API, non-thinking mode; requires `DEEPSEEK_API_KEY`). If both LLMs fail, falls back to rule-based `_fallback_recommendations()`. The source model name is logged at INFO level (`via <model>`). Parsed responses are **deduped per ticker** (first occurrence wins, `_dedupe_recommendations`) — LLMs occasionally repeat tickers (DeepSeek 2026-06-11) and every downstream consumer assumes one recommendation each; `record_new_trades` independently adds batch-opened tickers to its `already_open` guard so a duplicate can never open twin trades.

### Adding a new data source

Three patterns depending on what the source produces:

1. **Per-ticker signal** (like sentiment/technical/insider): implement `[-1.0, +1.0]` scorer, add weight in `aggregator.py`, add `enable_*` flag in `settings.py`. Also add the method to `tracker._ALL_METHODS` **and** `schema.SIGNAL_BASE_METHOD_COLUMNS` (the trade-attribution set + signals-table column; `ALTER TABLE signals ADD COLUMN <m> DOUBLE` on an existing DB) — `tests/test_db_signals.py` fails if the two drift. (`SIGNAL_METHOD_COLUMNS` = the base set + the panel-only `SIGNAL_TIMEFRAME_COLUMNS` multi-timeframe columns; an OHLCV scorer that should also be computed on the 30-min/weekly candles goes in `multi_timeframe.TECHNICAL_METHODS`.)
2. **Smart money signal** (like options flow, SEC filings): return `List[InsiderTrade]` from a new module, call from pipeline in the Step 3 block, extend `smart_money` list.
3. **Macro context** (like FRED, COT): return a new Pydantic model, pass to `generate_recommendations()` as an optional parameter, build a prompt block + instruction section in `claude_analyst.py`, render in email HTML template.
4. **News-like source** (like Google News, FDA, Reddit, Quiver, provider news): return `List[NewsArticle]` (ticker-tagged where possible; or pre-scored via `provider_insights` to skip the LLM scorer), submit it `_safe`-wrapped in the Step 1 fetch pool, add the result to `_article_chunks` (the merged-then-deduped pool), and add an `enable_*` flag. An always-on feed expected to return data stays OUT of `data_quality.EXPECTED_SPARSE_SOURCES` (so an empty result alerts); an optional/event-driven one goes IN. Real-time feeds belong on the fresh-every-tick lane (not the hourly cache).

A 403 on an endpoint is logged once per endpoint-family then suppressed (entitlement limit, not transient). Falls back gracefully when `POLYGON_API_KEY` is absent — `is_available()` returns False and `market_data.py` routes everything through yfinance instead. Free Polygon tier covers all US equity/ETF tickers; indices (^VIX etc.) and futures (GC=F etc.) must use yfinance directly.

**Bulk vs execution pricing — two separate paths.** The **bulk snapshot** (`market_data.get_snapshots`, Step 2: Polygon batch → yfinance → deterministic grouped-daily close) feeds the analysis panel (`signals.price`), scoring context, ext_gap, and the price-provenance check. **Trade execution** prices come from a different, robust path — `tracker._fetch_price` (IBKR real-time → yfinance → Polygon single-ticker), fetched live only for the handful of actionable/held tickers. A live intraday price is inherently non-deterministic (a moving quote); the deterministic, reproducible anchor used for analysis/NAV/IC is the completed daily CLOSE. The price-provenance check (`_assess_price_provenance`) compares each new trade's `entry_price` against the run's snapshot, skipping `price_source != "live"` anchors so a live fill is never falsely flagged against a prev-close fallback.

**Silent-default health monitors** (`pipeline._collect_sources` → `run_sources` → Data Quality tab + email/dashboard banner): three decision-feeding computations that used to fail invisibly now expose per-run health — **FX sizing rate** (`broker/fx.py`: live-quote vs static-fallback conversions), **correlation sizing** (`performance/correlation.py`: % of pairs that failed to compute → a silently weakened concentration haircut), and **macro-regime / market-mode input coverage** (how many feeds the composite actually used). Each keeps a reset-per-run module health dict; an unhealthy state surfaces as a source-health row, mirroring the LLM/broker/price health verdicts.

**SEC EDGAR rate limit:** 10 requests/second. All EDGAR calls use `_REQUEST_DELAY = 0.12–0.15s`. The `_ticker_index` (name→ticker) and `_ticker_cik` (ticker→CIK) maps are module-level globals populated once per process — never re-fetch them in a loop.

**yfinance rate limits:** When a 429 is returned, `market_data.py` applies exponential backoff (60s → 120s → 240s). After 3 failures the loop stops early. Options chain scanning (`options_flow.py`) is silent-fail per ticker.

**CFTC downloads:** The COT ZIP files are ~5–10 MB each. Both current and previous year are fetched if the current year has insufficient history. Always check the cache first.

**Actionable signal threshold:** Baseline (NEUTRAL regime) is `confidence ≥ 0.85` (Gate 1, mechanical) AND `sources_agreeing ≥ 2` (Gate 1b, mechanical since 2026-07-20 — `settings.enable_agreement_gate` / `min_sources_agreeing_gate`; before that date this was ONLY a prompt instruction the LLM was trusted to self-apply, with no code-level check — a 2026-07-20 audit found the gap). **Smoothed-step threshold (2026-07-27, `macro_regime.continuous_threshold`, `enable_continuous_regime_threshold` default ON).** The step table below was a CLIFF: composites of −0.801 and −0.799 sit in different regimes, and the live composite has **sd 0.146** — that boundary is well inside one standard deviation of ordinary daily variation, so the same market sampled two ticks apart could jump the actionable bar a full step (0.89 → 0.87). Each band now keeps its documented threshold throughout its interior; only within `_THRESHOLD_SMOOTH_HALFWIDTH` (0.05) of a boundary does the value ramp between the two neighbours, and **the ramp sits entirely on the LENIENT side** — the stricter band holds its value right up to the edge, because a symmetric ramp pushed NEUTRAL below 0.85 near the RISK_ON boundary and 0.85 is a user directive, not a tunable. Measured effect over the 230 observed live composites: **26 runs changed, mean +0.0012, max +0.016, none loosened, NEUTRAL still ≥0.85 everywhere.** NOTE a full band-to-band interpolation was implemented FIRST and rejected on measurement — it raised the bar on **100% of runs (mean +0.0089) and would have dropped 7.9% of actionable trades**, a systematic tightening rather than the removal of an instability; it is easy to "fix the cliff" and silently move the gate. The regime LABEL and the BUY block stay step-based (state decisions — a half-blocked BUY is not a meaningful thing), as does everything reading the label: exits, `macro_regime_exit`, and all the regime analysis. **The regime is deliberately NOT a per-ticker scoring method**: it is a single market-wide value, so adding it to `combined_score` would shift every ticker equally without changing the RANKING, its Spearman IC would be undefined (a constant has no rank variance) and it could never earn weight through the IC machinery — it is a STATE, not a signal. On the exit side it already IS scored (`_REGIME_PRESSURE` → the `macro_regime` exit method) but is correctly kept out of `exit_method_consensus`, because the regime already has a hard exit path and feeding it to the consensus too would double-count it. Tests: `tests/test_regime_threshold.py`.

The Macro Regime Filter adjusts the confidence threshold dynamically (`macro_regime._REGIME_THRESHOLD`): RISK_ON → 79%, CAUTION → 87%, RISK_OFF → 89%, PANIC → 95% (2026-07-21: the whole table was shifted a uniform +7 pp so the NEUTRAL baseline is 0.85 — the "minimum confidence" — while the regime filter's relax-when-calm / tighten-when-risky dynamics are preserved; this is NOT a hard floor, RISK_ON still sits below 0.85 by design). Runs outside RTH add `extended_confidence_bump` (+6 pp, capped at 95%) on top of the regime threshold — thin extended books demand more conviction. BUY entries are additionally blocked entirely during PANIC and RISK_OFF regimes. A single strong signal source never produces a BUY/SELL regardless of score. **Gate 1b scope:** `sig.sources_agreeing` (post win-rate-filter, effective/inversion-corrected sign — see the aggregator weighting-stack note above) is only a meaningful count for THIS call when the LLM's own recommended direction matches the aggregator's own `sig.direction` (the ~96% common "echo" case, 2026-07-12 agreement study); a genuine LLM override (`r.direction != sig.direction`) has no correctly-attributable agreement count and passes Gate 1b unchecked, governed only by the confidence threshold + prompt instructions, same as before this gate existed. Counted in `gate_diag.dropped_low_agreement` + the per-ticker `gate_outcomes` stamp (`"low_agreement"`); evaluated end-to-end (pass vs. drop, simulated performance) by `tracker.compute_stage_eval`'s decision funnel, visible on the dashboard's Entry Performance tab as the "Gate 1b" survivor/drop rows — inserted between Gate 1 and Gate 2 without renumbering the existing Gate 2/3/4 (BUY-block / earnings-blackout / liquidity-floor), which are referenced by number elsewhere in this file and in the dashboard. **Gate 5 — overextension / anti-chase (2026-07-22, BUY-only, `enable_overextension_gate` default ON):** the BUY-vs-SELL forensics (signals panel, 8.3k ticker-days) found the BUY side's core failure is CHASING — 40% of BUY calls landed in the top quintile of trailing-5d gainers (2× the universe share) and hit 38% at 5d (median −2.4% vs SPY); recent big gainers mean-revert (universe Q5 P(up) 45%, sweet spot = the mild-pullback Q2 at +0.64%) while `combined_score` peaks exactly post-run-up (momentum+tech+news all read the same move — the top score decile is the panel's WORST cohort, P(up) 38%, and within positive scores higher score → worse return, IC −0.099). The gate drops an actionable BUY whose trailing close-to-close return over the last `overextension_lookback_bars` (5) completed daily bars exceeds `overextension_runup_pct` (12%, from a threshold sweep: the blocked cohort hit 32.5% with −4.1% median vs kept 43.4%; 10–15% is a plateau so 12 is not knife-edge; vol-normalized variants separated WORSE than raw %). DEFERRED, not banned — the name re-qualifies at any tick it has cooled below the bar (entering on the pullback is the measured sweet spot). SELLs are NEVER gated (SELLs on crashed names ride continuation at 61.9%, SELLs on spiked names fade correctly at 64% — the asymmetry is real edge). Fail-OPEN on missing/short cached history (opportunity filter, not a risk guard — the liquidity gate owns thin data). `pipeline._is_overextended` / `_recent_runup_pct`; counted in `gate_diag.dropped_overextended`, stamped `"overextended"`, funnel rows "Gate 5" in `compute_stage_eval`. ### Broker integration (paper-first live execution)

`src/broker/` adds a real **execution leg** alongside the internal NAV simulator — a "shadow & reconcile" design for moving toward live trading. Gated by `settings.broker_mode`; **`off` (default) makes zero broker calls** (behavior unchanged).

- **Modes:** `off` | `dry_run` (log intended orders, submit nothing) | `ibkr_paper` | `ibkr_live`. Paper vs live is the configured `ibkr_port` (IB Gateway 4002/4001); the factory refuses to start `ibkr_paper` on a known live port.
- **Broker = Interactive Brokers** via `ib_async` → IB Gateway. It's the only API broker that lets a Canadian resident paper *and* live trade US securities (CIRO blocks API orders only for Canadian-listed names; the tradeable universe is 100% US stocks/ETFs). `ib_async` is imported lazily, so the package imports fine without it (off/dry_run paths).
- **Single hook point — `reconcile.sync()`** runs once per tick in `pipeline.run_pipeline()` right after `record_new_trades` (the ledger is final there). Idempotent and self-healing, in order: (0) **fill refresh** — orders submitted on an earlier tick that hadn't reached a terminal state inside `submit_order`'s ~12 s poll (queued overnight, partial fill, late commission report) are repaired from today's executions via `Broker.get_fills()` (IBKR `reqExecutions`, keyed by `orderRef`); (0b) **tick-scoped order lifetime** (`broker_tick_scoped_orders`, default on) — an order lives exactly one tick: anything submitted before this sync and still unfilled is cancelled and its leg cleared, so the entry/exit pass below resubmits THIS tick re-anchored at the current mark under a fresh `-rN` client_ref — entries resubmit only when the trade survived this tick's signal pass (`monitor_open_positions` runs first; a closed trade's entry dies via cancel-on-close) AND clear the **price-aware resubmit gate** (`broker_price_aware_resubmit`, default on, `_resubmit_decision`, 2026-07-07): a previously-unfilled entry chases only when the fresh signal STILL wants it (ticker actionable, same direction) OR the current price is as-good-or-better than the decision (≤ entry for a long / ≥ entry for a short); a decayed-signal-at-an-adverse-price entry is HELD this tick (`RESUBMIT_HELD_ADVERSE`, re-evaluated next tick) and a signal flipped to the opposite side is not resubmitted — EXITS are never gated (they always resubmit to get flat). The tick's actionable set is threaded into `sync(actionable_by_ticker=…)`; with none supplied it falls back to the legacy always-chase. So no order ever works the book on a previous tick's decision or price (`broker_unfilled_cancel_minutes` is the age fallback when tick-scoping is off; partial fills are left working; a cancel that loses the race to a fill is left for the fill-refresh pass). **Dead/expired orders are recovered**: every off-RTH submission is a DAY LMT that IBKR expires at the 20:00 session close — when the cancel finds nothing working and the ref has no fills today, the leg is cleared as `EXPIRED` and re-sent instead of resting as a zombie `Submitted` forever; entry legs are only cleared when no broker position backs them (day-scoped fills feed can miss a prior-day fill — resubmitting against a held position would double it), and a dead exit with nothing held is stamped terminal (an exit sized from the recorded entry fill would open a fresh short); (0c) **cancel-on-close** — a trade the ledger CLOSED while its entry order was still working gets that order cancelled immediately (`_cancel_entries_for_closed`): this was the orphan factory — nothing else would ever cancel it, and a later fill would create a position with no open trade behind it; any partially-filled part is flattened by the exit pass; (1) internal OPEN trades without a `broker_order_id` → sized entry submitted; (2) internal CLOSED trades still holding a broker position → close submitted, **sized from the actual held position when the positions feed has a row** (sign-checked — a wrong-sign holding is never blind-traded; falls back to the recorded fill qty when the feed has no row) so lagging fill counts leave no residue; (3) **drift** — broker positions the ledger cannot explain. In-flight closes are exempt (a CLOSED trade's working exit order, or an exit submitted this tick — the positions snapshot predates it). True orphans are handled per `broker_drift_action`: **`"flatten"` (default)** submits a price-capped marketable LMT at a fresh live quote (never adopted into the ledger — an adopted trade the strategy never signalled would contaminate every metric), re-cancelled + re-anchored each tick while it rests; a **same-side flatten that already FILLED within the last ~90 min blocks a resubmit** (`_recent_flatten_fill` — the positions snapshot can lag a fill, and a duplicate would FLIP the position, not flatten it; opposite-side fills never block, so an over-flatten correction goes through; unreadable fills fail closed to `flatten_skipped`); `"report"` is the legacy surface-only behavior; **`ibkr_live` always refuses auto-flatten** (downgraded to report — auto-selling unexpected real-money positions is a human decision). `IBKRBroker.get_positions()` does a blocking `reqPositions()` refresh before reading — `ib.positions()` is a subscription cache that only advances while the event loop runs, so on the long-lived singleton connection it could be a full tick stale by sync time. (4) **settle — fill fast or kill** (`_settle_unfilled_this_tick`, `broker_settle_seconds`, default **30** — lowered from 60 2026-07-07; 0 = legacy resting): after submissions, THIS tick's unfilled orders are actively watched — fills are repaired the moment they land (`broker_settle_poll_seconds`, default 3 s), a zero-fill order is cancelled and **re-anchored at a fresh live quote EARLY and REPEATEDLY** — every `broker_settle_reanchor_every` polls (default 2 ≈ 6 s), each a fresh `-rN` capped LMT chasing the spread in bounded steps instead of one re-anchor at the halfway mark — and at the deadline survivors are **CANCELLED** so nothing ever rests across ticks: an order either executes within ~a minute of its decision or it does not exist (the next tick re-decides from fresh signals and prices — an entry only comes back if the trade survives that tick's monitor pass; an exit always comes back until flat; partial fills are left working; drift flattens keep their own per-tick re-anchor). This is also the structural fix for late fills — the raw material of every stale-snapshot drift race. Every broker call is exception-safe — a failure logs and degrades to report-only, never breaking the run. The internal NAV sim stays the source of truth for analytics. **`tracker.py` is not modified.**
- **Order-vs-ledger durability (2026-07-23 drift cascade fix)**: the invariant is **no order may work the book unless a ledger leg points at it**, in both directions. It was broken in both. (1) `sync()` persisted ONCE at its very end, but the 600 s watchdog force-exits with `os._exit(1)` (no `finally`, no flush) — a kill mid-reconcile left orders LIVE at the broker with no ledger record, so the next tick resubmitted the SAME `client_ref`. (2) IBKR does not dedupe `orderRef`, and `cancel_order` `return`ed after its FIRST match, so it cancelled one of a stack per tick while the resubmit loop added more. (3) The settle budget was spent as a POLL COUNT (`n_polls = budget // poll_seconds`) while each poll's work (cancel ~1 s + re-anchor submit ~12 s, **per leg**) is unbounded — with ~9 legs a 30 s budget ran 10–20 min, so **every** tick blew the 600 s watchdog, which force-exited and orphaned that tick's orders: a self-reinforcing runaway (13 kills on 2026-07-23; 88 working orders, 18 refs duplicated, one HQY exit ref stacked 8 deep → all filled in the same second → 112 shares sold against a 14-share long → the position read as "drifted from the ledger" every tick thereafter). Five fixes: **`_persist_legs(trades, changed)`** flushes the ledger immediately after every submission (entry, exit, settle re-anchor) so the live-order-unknown-to-ledger window is milliseconds, not minutes (fail-soft; the end-of-sync save stays the backstop) — via **`repo.update_trade`**, which rewrites only the row matched on its stable `trade_id` (**53 ms vs 227 ms** for the full-table `save_trades`, so a 10-order tick no longer spends ~2.3 s re-writing unchanged rows) and DECLINES the fast path when that id isn't unique (it is only a ticker+timestamp hash, so a targeted `DELETE` could take out a duplicate too) or when the row is unknown, falling back to the full save either way; **`_settle_unfilled_this_tick` takes a real `time.monotonic()` deadline**, checked before each poll AND before each re-anchor submit, so `broker_settle_seconds` is wall-clock again; **`cancel_order` cancels EVERY order matching the ref** and confirms them all (a fill anywhere in the stack ⇒ not-cancelled, so the fill-refresh pass owns it) and warns when a ref had duplicates; **`_working_order_for_ref`** is a pre-submit duplicate guard (`_known_order_result` only ran before a *retry*, so a first submission could always stack) that adopts an already-working ref instead of sending — counted as `duplicate_submits_blocked`; and **`_sweep_orphan_orders`** runs at the top of every sync, cancelling working orders no ledger leg owns (`broker_orphan_order_sweep`, default on) — counted as `orphan_orders_cancelled`. Drift-flatten refs (`drift-<TICKER>-`) are exempt (no leg by design; `_flatten_orphan` runs its own cycle), and hand-placed TWS orders are exempt because they carry no `orderRef` and `get_open_orders` drops ref-less orders. `IBKRBroker.connect()` now also calls `reqAllOpenOrders()` so a relaunched scheduler SEES its prior sessions' still-working orders — without that binding, all three of the cancel/guard/sweep fixes are blind across exactly the restarts that cause the problem. Tests: `tests/test_broker_reliability.py`.
- **Right-sized on the first order (2026-07-23)**: two rules keep a repeat submission from compounding. (1) **Size the GAP, not the target** — an entry subtracts what the broker ALREADY holds in the same direction before ordering (`positions.get(ticker)`, same-sign only; an opposite-sign holding is the drift pass's business, not an offset to trade against). A position already at/over target submits nothing (`POSITION_ALREADY_AT_TARGET`), so a duplicate or an unrecorded prior fill is self-limiting — it asks for 0 instead of doubling. This also means the 23 oversized positions left by the cascade are never added to. (2) **Never chase a runaway price** — `_resubmit_decision` now applies its adverse-price ceiling (`broker_resubmit_max_adverse_bps`, default **100 bp**, 0 = disabled) to EVERY entry resubmit, not only to ones whose signal had decayed. Previously `cur == action` returned `submit` immediately, so a still-actionable name was re-sent at any price however far it had run from `entry_price` — the price the decision and its sizing were made at. Order of checks: opposite-side flip → skip; adverse beyond the ceiling → skip (`RESUBMIT_HELD_ADVERSE`); still actionable inside the ceiling → chase; decayed → only at an equal-or-better price. EXITS are never gated — an exit must get flat regardless of price. Tests: `tests/test_broker_price_aware_resubmit.py`.
- **Submission reliability (`_submit_with_retry`)**: every submit's broker answer is verified. **Transient** failures (connection drop, timeout, pacing — classified by `_is_transient_failure`) retry up to `broker_submit_retries` (default 2) with `broker_retry_wait_seconds` (default 5 s) pauses — a deliberately SHORT window so a delayed fill stays anchored to the tick's model price; **hard rejects** (insufficient funds, permissions, invalid contract) never retry. Before each retry a **duplicate guard** (`_known_order_result` via `Broker.get_open_orders()` + `get_fills()`) checks whether the errored attempt actually reached the broker — if so the existing order is adopted, never resubmitted (orderRef is a tag; IBKR does not dedupe, so a blind retry would double the position). Every retry is converted to a **marketable LMT capped at `broker_limit_cap_bps`** from the model price (even when `broker_order_type=MKT`), so the worst acceptable fill never drifts past the cap no matter when the retry lands. Failed attempts persist as `SUBMIT_FAILED` rows in `broker_orders`; stale cancels as `STALE_CANCEL` rows; settle activity as `SETTLE_FILL` / `SETTLE_REANCHOR` / `SETTLE_KILL` rows; per-run `retries` / `stale_cancels` / `settled_fills` / `settle_reanchors` / `unfilled_killed` counters ride the report. **Connect retries:** `sync()` retries the gateway connection at start (`broker_connect_retries`, default 2 × 10 s) — IB Gateway's daily re-login window otherwise costs a whole tick's order cycle (observed 2026-06-11 15:41). **Auto-reconnect (2026-07-11):** a session that DROPS (gateway restart, network blip, re-login) self-heals at the next broker touchpoint — every `IBKRBroker` method gates on `_ensure_connected()`, which redials a disconnected session before failing soft, so a mid-tick drop recovers mid-tick (price fetches, cancels, fills — not just the next sync's connect loop) and the tracker's IBKR price feed comes back on its own. A failed dial arms `broker_reconnect_cooldown_seconds` (60 s) during which implicit revives fast-fail — a down/wedged gateway can't charge every touchpoint the 15 s `ibkr_connect_timeout` (tracker/borrow-context no longer call `connect()` per call for the same reason); explicit `connect()` calls (the sync-start retry loop, `_submit_with_retry`) bypass the cooldown and a successful dial clears it. `connect()` also resets half-dead client state (`ib.disconnect()` before redial) and `disconnectedEvent` logs the drop the moment it happens. Tests: `tests/test_broker_reconnect.py`. The alive-but-wedged gateway (port open, API dead, `isConnected()` still True) remains the watchdog/IBC's job — reconnect only fires once the session actually reads as dropped. **Request timeout + sync watchdog (2026-07-06 freeze fix):** a stuck ib_async request (`reqExecutions`/`reqPositions`/`placeOrder`) with no timeout froze the ENTIRE poll loop for 6 h (01:12→07:xx, all ticks + the 04:00 email missed — a HANG, so neither Task-Scheduler restart-on-failure nor `--supervise` caught it: the process never exited). Two-layer fix: (1) **`IB.RequestTimeout` = `broker_request_timeout_seconds`** (default 45 s, set in `ibkr._get_ib()`) bounds EVERY ib_async API request — the primary fix, so a wedged broker call raises instead of hanging and the tick continues; 0 = legacy no-timeout. (2) **A `threading.Timer` watchdog** around the whole `_broker_sync` (`broker_sync_watchdog_seconds`, default 600 s) is the hard backstop — on expiry it logs CRITICAL and `os._exit(1)`, converting a hypothetical un-bounded hang into a fast death the supervisor recovers. This is exactly why the scheduler now runs under `--supervise` (below) by default — the watchdog's force-exit is only useful if something relaunches the child.
- **Order types:** `broker_order_type` = **`LMT` (default)** or `MKT` — a **marketable limit** at the model price ± the **session's cap** in the adverse direction (rounded away from the model to a valid tick): `broker_limit_cap_bps` (20) during RTH, `broker_limit_cap_bps_extended` (80 — the extended-book spread runs ~4× RTH, matching the sim's 4× cost multiplier; a 20 bp cap sits inside the extended spread and can never fill) off-hours. The cap bounds the worst acceptable fill; an order whose cap is missed is re-anchored in-tick by the settle pass and killed if still unfilled, so LMT no longer trades fill-speed for price protection (MKT has no bound at all — observed −107 bp/−91 bp RTH fills on thin books 2026-06-12). The design goal is **fill in the decision tick at the current spread** rather than later at a drifted price. **Off-RTH ticks override the configured type**: IBKR rejects MKT outside regular hours, so extended-session submissions are always marketable LMT with `outsideRth=True` (`OrderRequest.outside_rth`); an order submitted overnight rests until the 04:00 pre-market open. Class-share tickers are normalised both ways (`to_ib_symbol`/`from_ib_symbol` in `ibkr.py`: yfinance `BRK-B` ↔ IBKR `BRK B`).
- **Execution measurement (persisted):** slippage is recorded for **entries and exits** as **cost-normalized bps** (positive = adverse for either side), alongside actual IBKR commissions captured from fills. Each `sync()` report — one summary row plus one event row per order submission / fill repair — is persisted to DuckDB (`broker_reconciles` + `broker_orders` tables, `repo.insert_broker_report`, called from `_persist_run`), so the paper phase accumulates a durable slippage/reject/drift record instead of losing it after each email. Each sync also captures the **account NAV** (`get_account`) and IBKR's **own account P&L** (`Broker.get_pnl` → `reqPnL`: `pnl_daily`/`pnl_unrealized`/`pnl_realized`, persisted on `broker_reconciles`) — ground truth incl. all fees/FX/dividends. `get_pnl` is fully fail-soft (its own try in `sync` — a broker without it or a `reqPnL` hiccup never aborts the reconcile) and best-effort/live-unvalidated (smoke-test before trusting, like `get_short_borrow`). It is account-level + today-scoped (`daily`/`realized` reset each session; `unrealized` is current open P&L), NOT per-round-trip — IBKR doesn't track the strategy's individual trades.
- **Sizing** (`sizing.py`): two modes via `broker_sizing_mode` — `notional` (default: fixed `broker_base_notional` in `broker_base_notional_ccy`, e.g. 2000 CAD, converted to a USD share budget via live FX in `fx.py`) or `equity_pct` (% of account equity). Both × the ledger's `position_size_multiplier` (the compressed-confidence × agreement-breadth conviction tiers, plus haircuts), with max-positions and max-gross-exposure caps (all USD-normalised, since US securities are USD-priced).
- **Reuse, not rebuild:** `broker_*` fields ride along in the DuckDB JSON `data` column (no migration); `recommendation_id` is the idempotent IBKR `orderRef` — and the reconciler enforces **one broker order per client_ref, ever**: IBKR does not dedupe orderRef, so a second ledger trade sharing a ref is skipped and durably marked `DUPLICATE_REF_NOT_SUBMITTED` (entry and exit passes share the per-tick ref set; a twin exit sized from the full held position would flip the book short); a broker-health verdict (`_assess_broker_health` in `pipeline.py`) mirrors `_assess_llm_health` → CRITICAL log + email banner (`broker_health` var) + `🔔 BROKER` subject tag on drift/rejects, plus a green "N entries / M exits / fills repaired / avg slippage" line when healthy. A **third verdict, `_assess_price_provenance`**, follows the same pattern (CRITICAL log + `price_health` email banner + `🔔 PRICE` subject + the dashboard's Execution tab): it flags any trade opened the run whose recorded `entry_price` diverged from the run's snapshot price beyond the session band (`price_provenance_band_{rth,extended,overnight}_bps`, default 100/350/600) — the standing, automatic version of the one-off stale-price (CRDO) audit. Its verdict is stashed in `gate_diag.price_provenance` so it persists for the dashboard with no schema change.
- **Ops:** IB Gateway must run alongside the scheduler and needs a ~daily re-login (use IBKR auto-restart + IBController). Before enabling: `python -m src.broker.smoketest` (connectivity), then `--order` for a 1-share round trip. **Gateway auto-recovery (2026-07-14, `src/broker/gateway_recovery.py`, `broker_gateway_auto_restart` default on):** the last manual ops step is automated — when the GATEWAY itself is the corpse (alive-but-wedged: process up, port open, API dead — IBC's watchdog can't see it; or fully down), `maybe_restart_gateway` kills the gateway java owning `ibkr_port` and fires the `'IBC Gateway'` scheduled task — **and when NOTHING is listening on that port it falls back to identifying the gateway by command-line SIGNATURE** (`_gateway_pids_by_signature`: `ibcalpha.ibc.` — IBC's launcher main class — or an `\ibgateway\` classpath entry; specific enough that an unrelated java app can never match, verified against a live gateway). That fallback exists because of a real 2026-07-26 incident: a gateway wedged for **~23 hours** with its process alive but port 4002 NEVER bound, so the port probe returned nothing, recovery logged *"pid not found"*, killed nothing, and fired the relaunch task on top of a surviving corpse — while IBC's own watchdog stayed happy because it only checks the process is alive, and it was. The listener still takes precedence when one exists (the scan is a fallback, and could match more than one process); the scan is fail-soft, so a failure degrades to the previous relaunch-only behaviour (relaunch + auto-login, paper needs no 2FA). Fired from the two places that KNOW the gateway is the problem: `reconcile.sync`'s connect-retry exhaustion (waits `broker_gateway_restart_wait_seconds` ≈90 s for the fresh port, then dials once more — saving THIS tick's order cycle) and `ibkr._ensure_connected`'s wedge-forced redial failing (fire-and-forget; next touchpoint redials). PAPER-ONLY — `ibkr_live` downgrades to a CRITICAL log (live re-login may need 2FA; same human-decision posture as drift auto-flatten); cooldown-guarded (`broker_gateway_restart_cooldown_minutes` 30) so a broken gateway can't be kill-looped; fail-soft throughout. Tests: `tests/test_gateway_recovery.py` (conftest pins `broker_gateway_auto_restart=False` suite-wide so no test can kill the real gateway).

**Inert-config guard (2026-07-25).** Three "looks configured, does nothing" bugs were found in one day (overlay inversion, unrecognised `inverted_methods` names, and the combined-score gate below), so `tests/test_inert_settings.py` now fails on any NEW setting that is defined and documented but read nowhere — flipping such a setting appears to work and changes nothing, with no error. Two independent samples agree that the LLM adds value exactly where the aggregator is undecided or wrong, so forcing agreement with the weighted methods removes its best cohort.
